# C — Background extensions' session-file writes, the foreign-SessionManager mechanism, and the fencing gates

Investigator session: 01a0a4c8-09b0-7451-bac8-3c94032b227c. Read-only; this file is the only artefact created.

## Summary

Background-work extensions persist registry snapshots into the session JSONL through `pi.appendEntry`, whose implementation is a closure over the SessionManager of the AgentSession that loaded the extension — not necessarily the session's *current* one. Every fresh extension binding over a file unconditionally appends an empty `bg-shell-tasks` + `background-tasks` pair at load (reconcile → persistNow), so any second runtime over the same file — a second AgentSession in the host, or an external `pi` process — leaves an append-only disk tail the live runtime never loads. auto-compact-75's freshness gates compare the disk entry sequence against the runtime's in-memory sequence; on 2026-09-15 (session 01a0a410) the `/autocompact75 handoff` gate ran with `fenceOnAppendOnly: true`, classified this host-induced tail as "session changed outside this runtime" and fenced the live session. v2.7.0 tolerates the tail at handoff/claim only; the writer is unfixed and the startup fence plus true-divergence paths remain exposed.

## 1. Which extensions write to a session file, through which object, at which moments

**The write primitive and its binding.** Extensions call `pi.appendEntry(customType, data)` (`pi-coding-agent/dist/core/extensions/types.d.ts:985`). `pi` is not global state: `ExtensionRunner` holds one `sessionManager` (`runner.js:119–127` — constructor stores `this.sessionManager`) and `bindCore()` copies the action closures onto the shared runtime object: `this.runtime.appendEntry = actions.appendEntry` (`runner.js:164`). The AgentSession builds its runner with *its* SessionManager: `new ExtensionRunner(extensionsResult.extensions, extensionsResult.runtime, this._cwd, this.sessionManager, …)` (`agent-session.js:2202`). So an extension's `appendEntry` lands in exactly one SessionManager: the one belonging to the AgentSession whose runner invoked the extension factory. The pi-enhancement extensions capture that `pi` object in closure scope and keep it: `let piRef: ExtensionAPI | null = pi` (`/root/pi-enhancement/background-shell/index.ts:79`).

**Writers, moments (all paths under `/root/pi-enhancement/` unless stated):**

- **background-shell** (`bg_run`/`bg_list`/`bg_output`/`bg_stop`). Persist callback wired at `background-shell/index.ts:135–141` via `createVerifiedPersist("bg-shell-tasks", …)`; implementation appends then read-verifies (`background-shell/core.ts:927–957`). Moments: task registered `core.ts:404`; process attached `core.ts:419`; task settled `core.ts:462`; orphan sweep in `list()` `core.ts:584`; session_start reconcile `core.ts:680` (**unconditional** — fires on every session load, even when nothing changed); `session_shutdown` persistNow for non-quit reasons `index.ts:440–457`; `session_before_compact` `index.ts:459`; retryFlush at session_start `index.ts:421–438`. Also writes a compaction reinjection message `bg-shell-tasks-reminder` via `sendMessage` at `index.ts:463–470`.
- **subagent extension** (its background-task registry — this is the writer of the `background-tasks` entries; the `background-tasks/` directory itself contains only `PLAN.md`). `BACKGROUND_ENTRY_TYPE = "background-tasks"` (`subagent/index.ts:59`); same vendored persist design (`subagent/background.ts:67–68, 416+`, persist call sites `background.ts:147, 162, 175, 231–232, 271`, and the unconditional load-time `persistNow()` at `background.ts:349`); session_start reconcile at `subagent/index.ts:1074–1083`, session_shutdown `:1090`, session_before_compact `:1103`.
- **watch-wake**: `persistRegistrations()` appends `watch-wake-registrations` (`watch-wake/index.ts:34, 239–251`) — fingerprint-gated since the 2026-09-06 incident so unchanged polls write nothing (`index.ts:234–240`); moments: poll tick with due/cursor changes (`index.ts:260–262`), startup reconcile `:292`, register `:340`, cancel `:382–384`; plus a best-effort `watch-wake-delivery` audit entry on fallback delivery `index.ts:207`. The deadline tool persists `watch-wake-deadline` records synchronously via `pi.appendEntry` (`watch-wake/deadline-host.ts:6, 85`; synchronous-only contract `watch-wake/deadline.ts:47–48, 78`).
- **goal-engine**: `saveGoalState` / `clearGoalState` append `goal_engine` entries (`goal-engine/state.ts:238, 260–263, 269–272`) on goal state mutations.
- **auto-compact-75 itself**: writes `auto-compact-75-safety` evidence entries (`auto-compact-75/index.ts:124, 448`).
- **agent-os-inject** (symlinked from `/root/.pi/agent/extensions/agent-os-inject`): does not call `appendEntry`; it returns injection messages `{customType: 'agent-os'}` (`agent-os-inject/emitter.ts:367`) that enter the session through the *current* runtime's normal message pipeline — the `custom_message agent-os` entries visible in the production JSONL. Memory and disk advance together, so it is not a disk-ahead writer, but it does add entries at every injected prompt.

## 2. What exactly they write — and the own-SessionManager question

**Entry shapes** (observed both in code and in the production file `/root/.pi/agent/sessions/--root-pi-web-ui--/2026-09-15T07-56-10-243Z_01a0a410-f683-7422-bc57-055af50db3f2.jsonl`, inspected read-only): all are `type: "custom"` lines — `customType: "bg-shell-tasks"` with `{tasks: ShellTaskEntry[]}` (incident entries `5aaa9bee` 08:18:52.179Z and `64f471d8` 08:21:01.442Z, both `tasks=[]`); `customType: "background-tasks"` with `{tasks: …}` (`59e8e57e` 08:18:53.010Z, `tasks=[]`); `customType: "watch-wake-registrations"`, `watch-wake-deadline`, `goal_engine`, `auto-compact-75-safety`; plus `custom_message` type `agent-os`.

**Do the extensions hold their own SessionManager?** They never construct one. They hold a **`pi` binding whose append action closes over exactly one SessionManager instance** — the instance of the AgentSession that loaded them (`runner.js:119–127, 164`; `agent-session.js:2202`). That binding becomes *foreign* in three code-backed ways:

1. **A second AgentSession over the same file.** The pi-web-ui server creates a fresh SessionManager + resource loader + extension set per `createSession` (`pi-service.ts:407` `SessionManager.open(...)`, `:443` `createSessionResourceLoader`, `:445` `createAgentSession`), and immediately binds extensions: "bindExtensions() emits session_start" (`pi-service.ts:467–468, 496`). Callers that can target an already-open path: `SessionPool.createClientSession/switchClientSession` (`session-pool.ts:38–75, 76–121`) and `MultiSessionManager` rehydration (`multi-session-manager.ts:778–852`). Each such open appends the empty snapshot pair through the *new* SessionManager.
2. **Extension closures outliving their AgentSession.** `AgentSession.dispose()` does **not** emit `session_shutdown` (`agent-session.js:584–601` — aborts, invalidates ctx, disconnects; no shutdown event), unlike `reload()` which does (`agent-session.js:2220`). background-shell clears `piRef` only inside its session_shutdown handler (`background-shell/index.ts:453`), so after a bare dispose (SessionPool replace `session-pool.ts:43, 81`; MultiSessionManager dispose/unload `multi-session-manager.ts:515–550, 564–583`) any later timer/callback that reaches `persistNow()` writes through the *old* SessionManager. Its `createVerifiedPersist` guard catches writes landing in the *wrong file* (`core.ts:938–956`), not writes landing in the *right file via a stale instance*.
3. **A separate OS process.** Any `pi` CLI invocation against the same `--session` file appends the same load-time pair; the host process cannot see another process's writes.

The production tail carries the exact fingerprint of path 1/3's *load-time* write: two empty-registry entries in bg-shell → background-tasks order ~0.8 s apart, with no `model_change`/message entries that a real turn would add (compare the confirmed fresh-open pair at 09:08:07/09 preceding the 09:08:30 `model_change`).

## 3. Gates that compare session-file state against in-memory state

The strict disk-vs-memory gates are **not in the server** — they ship inside the auto-compact-75 extension, which runs inside every hosted pi session. Server search (`mtime|fingerprint|freshness|stale` over `/root/pi-web-ui/server/src`) found only display/cache uses (e.g. `session-registry.ts:463`, `internal-api/routes/sessions.ts:782–794, 4749–4764`) and no freshness fence. The pi runtime itself has none.

## 4. The specific mechanism of the handoff refusal

Recorded evidence: `/root/pi-web-ui/operations/change-requests-20260915/child-handoff/complete.md` §1–§2 (refusal and fence at 2026-09-15T08:20:14, "disk entry sequence differs from the loaded session (157 on disk, 155 in memory)"; disk-only tail = `5aaa9bee` custom/bg-shell-tasks + `59e8e57e` custom/background-tasks). I verified against the production file and the host journal:

1. 08:13:22 — the live Web UI runtime's last turn entry lands; its in-memory count is 155. 08:18:04 / 08:19:27 — browser clients switch viewing to the session (`journalctl`: `[handleSwitchSession] … switched from none to …01a0a410…`); no AgentSession is created, disposed or rehydrated (the journal window 08:17:30–08:21:10 contains no `Rehydrating session from disk` / `Session rehydrated` / `dispose` lines, and every in-process creation path logs: `multi-session-manager.ts:779, 851`, `session-pool.ts:50, 67, 117`, stale-stream dispose `:431`). Yet at 08:18:52.179/53.010 the pair `5aaa9bee`/`59e8e57e` (both `tasks=[]`) was appended. **A SessionManager other than the live one wrote to the file** — by §1's binding analysis, a fresh extension binding performing its unconditional load-time persist (`core.ts:680`, `background.ts:349`), i.e. a second runtime opened the file (external `pi` process, or an in-process path that logs nothing — see §6).
2. At 08:20:14 the operator sent `/autocompact75 handoff` over the browser WebSocket; `AgentSession.prompt()` resolves extension commands before any ownership guard (complete.md §2), so the extension handler ran on the still-155-entry runtime. v2.6.0's `beginOwnershipHandoff` called `verifyCompactionSafety(ctx, { requireMemoryContentMatch: true, fenceOnAppendOnly: true })` with no pre-adoption.
3. `inspectSessionFreshnessOnce` read the file (157 entries), compared id sequences against memory (155) — `sameSequence` false (`session-ownership.mjs:530–534`) — and classified: memory ids are an ordered subsequence of disk ids, so `appendOnlyDiskAhead: true, canFastForward: true` (`:545–575`). The failure reason string is exactly the refusal text: `` `disk entry sequence differs from the loaded session (${disk} on disk, ${memory} in memory)` `` (`:557`).
4. Because `fenceOnAppendOnly: true` disables the v2.3.0 deferral (`index.ts:415–419`), the gate took the fence branch: `fenceOwnership("session changed outside this runtime: …")` (`index.ts:423–425`). The fence then blocks subsequent chat input (`index.ts:1076–1083`, "Session input blocked…") and all tool calls (`tool_call` handler `:1085–1088`) until a resync — the operator-visible symptom.

**Why v2.7.0's tolerance is sufficient for this symptom.** The tail is whole-line, append-only growth by host-resident extensions. v2.7.0 (a) makes the source adopt the tail before gating — `adoptAppendOnlyDiskTail` reloads the file through `SessionManager.setSessionFile` so memory == disk and the pinned whole-file fingerprint includes the tail (`index.ts:331–335, 617–665`); and (b) makes the target's claim tolerate the *target's own* load-time pair via the byte-length prefix proof (`session-ownership.mjs:433–462`) — the second, independent failure half proven in complete.md §2/§5. Both sides now treat exactly the class of change the foreign writer produces as adoptable, while any non-append change still fences. It tolerates the symptom; it does not remove the writer.

## Residual risk per gate

- **G1 startup fence — still exposed (moderate likelihood, high annoyance).** A foreign append landing between the runtime's own file load and auto-compact-75's startup freshness check fences the session at birth (`index.ts:294–302`). The writer fires on *every* session open, so any concurrently opening second runtime (Web UI rehydration racing a CLI open, or two opens racing) can hit the window. A same-runtime write is safe (it is in memory before the check).
- **G2 75 %/compaction gate — low residual.** Append-only tails defer and adopt (`index.ts:414–421`, `:958–990`). Trip risk remains for *non-append* disk changes: a torn/partial line from concurrent appenders, an editor rewrite, or a writer that modifies prior entries. All current extension writers are append-only, so this needs an unusual actor.
- **G3 handoff gate — low residual.** Post-adoption it still refuses any non-append divergence; only adoption failure (divergence arriving mid-adoption) fences, which is correct behaviour.
- **G5 claim pin — low residual.** Prefix proof accepts exactly whole-line growth; old leases without `sessionBytes` fail closed.
- **Cross-cutting: unbounded session growth.** The unconditional load-time persist (`core.ts:680`, `background.ts:349`) adds one pair per runtime open; Web UI dispose/rehydrate cycles (idle cleanup `multi-session-manager.ts:466–493`, stale-stream `:431`) each grow the file. This is what made pre-2.7.0 handoff/claim unusable here (complete.md §3) and it continues indefinitely.
- **Cross-cutting: stale-binding re-queue loop.** After a session switch, a surviving old binding persists into the *old* file; `createVerifiedPersist` detects the mismatch and re-queues (`core.ts:938–956`, surfaced as the widget warning `index.ts:95–97`) — contained, but each retry is another foreign write somewhere.

## What I could not determine

- **The actor behind the 08:18:52/53 tail.** The host journal excludes every logging in-process creation/dispose path, pointing to a second process (an external `pi` invocation against the file); CLI-side sessions keep no central log I could find, and I could not correlate shell history for that minute. I cannot fully exclude an unlogged in-process path — `PiService.createSession` logs nothing on the open-existing branch (`pi-service.ts:427`) — but every current caller of it logs. This is the load-bearing honest gap: the *mechanism* (a second SessionManager appending the load-time pair) is proven; the *invoking event* is not.
- Whether any extension instance survived a bare `dispose()` and later wrote through its stale binding in this incident (architecture supports it — `agent-session.js:584–601` emits no shutdown; no direct evidence it happened here).
- The deployed auto-compact-75 version at 08:20 was v2.6.0 per complete.md §7 ("deployed mirror … still v2.6.0"); I did not independently verify the runtime copy.
- I could not run any test suite or build (read-only constraint); all findings are from code and artefact inspection.

*Fix direction (one line, not scoped here): make extension session-file persistence rebind-safe (route through the session's current SessionManager) and gate the load-time reconcile persist on a change fingerprint (as watch-wake already does, `watch-wake/index.ts:236–251`), optionally under a server-side single-owner residency claim.*
