## 1. What was fixed

Two retention paths held state for session files that had been deleted. Both are
in `server/src/pi/session-watcher.ts`.

1. **`SessionWatcher.debounceTimers`.** `handleChange('unlink')` called
   `clearTimeout` on a pending debounce timer but never removed its map entry.
   Every session file added and unlinked inside the 500 ms debounce window left
   a fired `Timeout` (and the per-path state its closure captures) in the map for
   ever. The unlink branch now deletes the entry.

2. **chokidar `awaitWriteFinish` per-file watch state.** chokidar 3.6.0's
   `_remove()` early-returns when a pending `add` is still inside its
   await-write window: it calls `cancelWait()` and returns **before** deleting
   the path from `_watched`, closing the per-file `fs.watch` (the retained
   `FSWatcher`) and emitting the unlink. Every session file created and deleted
   before it was declared stable therefore left a permanent `FSWatcher`, its
   `_watched` path entry and the `Stats`/`Date` objects its listener closure
   holds. `awaitWriteFinish` is removed; the watcher already debounces (500 ms),
   reads the header itself and coalesces reads, so the library-side stability
   wait added no correctness — and unlinks for rapid churn are now delivered
   instead of silently dropped.

The retainer evidence from the confirmation soak and the mechanism are quoted in
§5. The library behaviour was read from `node_modules/chokidar/index.js`
(`_remove`, `_awaitWriteFinish`, `_throttle`) and reproduced directly (§4).

## 4. The retention mechanism, reproduced directly

A standalone probe (a real chokidar watcher through `SessionWatcher`, churn
pattern identical to the harness) confirmed both paths before the fix:

- Pre-fix, 200 files/case: `debounceTimers` retained **143** entries,
  chokidar `_watched` retained **32** file keys and `_closers` **45**.
- Pre-fix, 1000 files/case: `debounceTimers` retained **1078** entries,
  chokidar `_watched` **177** file keys, `_closers` **190**.
- With `awaitWriteFinish` disabled (the fix), 20 rapid create/delete cycles
  left `_watched`, `_closers` and the live `fs.watch` count flat, and both add
  and unlink were delivered for every file.

Chokidar `_remove()` early return (read from `node_modules/chokidar/index.js`):

```js
// If we wait for this file to be fully written, cancel the wait.
if (this.options.awaitWriteFinish && this._pendingWrites.has(relPath)) {
  const event = this._pendingWrites.get(relPath).cancelWait();
  if (event === EV_ADD) return;      // <-- returns before _watched.delete / _closePath
}
```

### 5.1 Churn design (and why the first timings failed)

3,000 files with a valid `type:"session"` header, 1,000 per case, in 12 fixed
child directories, `before`/`after` forced-GC snapshots:

| case | lifetime | targets |
|---|---|---|
| `before-stability` | ~300 ms | file seen by chokidar's directory read, deleted before `awaitWriteFinish` declares it stable |
| `inside-debounce` | ~700 ms | unlink after the add but inside the 500 ms debounce window |
| `after-debounce` | ~1200 ms | control: debounce already fired and emitted |

**Finding (cost a false-negative first run).** With very short lifetimes
(15 ms/400 ms) the old build showed almost no growth: chokidar's directory
readdir/AWF latency means a file deleted too quickly is never observed at all,
so neither retention path is entered. Timings of 300 ms/700 ms/1200 ms reproduce
both paths reliably. The final `buildPlans` defaults encode this.

## 9. Residual risks

- **Change-event frequency.** Removing `awaitWriteFinish` means the watcher's
  synchronous 16 KiB header read now runs on each raw change notification rather
  than after a stability wait. chokidar still throttles `change` to 50 ms per
  path; the read is bounded and was already exercised by the coalescing tests.
  The micro's CDP lag proxy stayed low (mean 1.0 ms, p95 1.0 ms, max 48 ms).
- **Add→unlink identity race.** With AWF gone, a session file created empty,
  written, and deleted before the first successful header capture falls back to
  the filename-derived id. A `change` notification normally captures the header
  within 50 ms; the existing `preserves the canonical id when add is immediately
  followed by unlink` test still passes.
- **Pi SDK watchers.** The micro's generic `FSWatcher`/`Stats` growth suggests
  per-session `fs.watch` handles from the SDK's theme/footer providers may be
  under-released. It is outside `session-watcher.ts` and is a candidate
  follow-up for whoever owns the SDK/extension lifecycle — flagged, not fixed
  here (scope).
- **Bursty churn stalls the disposable server.** A 200-files-per-batch burst
  produced a 20–23 s event-loop stall and shed-mode alert on the throwaway
  validation server. The finalised 40/batch timing did not. This is a synthetic
  load artifact, but it may be relevant to B1.2's lag attribution.

## 11. Correction round — live-session read amplification (parent verification, 2026-09-28)

The parent verification found one major issue: removing `awaitWriteFinish` fixed
the **deleted**-file retention but also removed chokidar's coalescing of
**change** events, which chokidar applies to live appends too. `handleChange`
started a complete-file read on the first notification of a window, and
`finishRead` chained a trailing read whenever another change arrived during the
read — so a large session being appended to during a turn could run back-to-back
`fs.readFile` + synchronous `JSON.parse` for the whole turn.

### 11.2 Fix

Reads are coalesced to the debounce window, inside `session-watcher.ts`:

- `handleChange` no longer calls `ensureRead` on a raw notification. It sets
  `revalidateQueued` and (re)arms the debounce timer; the header capture stays
  synchronous and bounded.
- `emitChange` (fire by the debounce timer, i.e. after the quiet period) starts
  at most one complete read through `waitForSettledRead` → `ensureRead`.
- `finishRead` no longer chains a trailing read. A change that lands during the
  read resets the window; that window's emit performs the next single read. So a
  continuously-appended file gets **at most one complete read per quiet
  period**.

### 11.6 Updated residual risks

- The synchronous 16 KiB **header** read still runs on each raw change
  notification while a path is changing (bounded, and the live-load run shows
  it is cheap: 585 header reads for 585 appends at p99 21.6 ms). Only the
  **complete-file** read is now deferred to the quiet period.
- Read coalescing means an event emitted right after a window close reflects
  the file as of that read; a change during the read is reported by the next
  window (≤ one debounce delay later). Consumers already handle repeated
  `change` updates and the identity is unaffected.
- The micro's generic Pi-SDK `fs.FSWatcher`/`Stats` growth remains a flagged
  follow-up outside `session-watcher.ts` (§5.5, §9).
