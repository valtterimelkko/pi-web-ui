## 3. Attribution (criterion 2)

1. **d1's freeze does not exist on master.** With G2's exact mock shape and a slower-than-G2 sync subscriber, r3's subscriber received all 11,818 deltas at a constant 25–26 ms cadence (worst gap 62 ms) across 300 s. A real 17.5-minute zai turn (r2) produced zero streaming stalls ≥50 ms after prompt dispatch. No shed trip, no slow-client close, no governor queueing in any arm (0 `[Connection] Closed slow WebSocket` lines; 0 queue events).
2. **The WS fan-out path is byte-identical between G2's build and master:** `git diff 8157d7d5..6a70238d -- server/src/websocket/outbound-governor.ts server/src/pi/stream-transport.ts` → empty; `connection.ts` differs only by H1's view-only opens (default off; `PI_WEB_UI_VIEW_ONLY_SUBSCRIBE` unset in every arm). No code fix in the lane's path explains the non-reproduction — G2's runs sat in a busy host window (its own c1 worst case was "host-amplified" at load 10.33), which is exactly what the L-pair probed (§4).
3. **The residual prompt-dispatch stall (114–281 ms, 8/8 arms incl. L-ctl) is subscriber-independent and is not a blocking function.** The r7 CPU profile of the server child (200 µs sampling, routed via `NODE_OPTIONS` to the detached child) shows **no continuous non-idle JS run ≥ ~390 ms anywhere in the turn**; the stall window itself is 89 % idle with small distributed work — SDK/extension module compile 33 ms, `writev` 21 ms, `spawnSync` 21 ms, GC 116 ms spread. The WS send path's entire self-time is ~35 ms per 20 s of 40/s streaming (`sendMessage` 13.4 ms + ws sender 12.3 ms + transport projection 9.2 ms). The lag reading is event-loop queue congestion / scheduling (the disposable unit runs at `CPUWeight=100`), not the WS path.
4. **The only ≥300 ms mechanism on master is the create-session `resource_loader` stall (444–594 ms, correctly attributed)** — a different, already-owned cost (G4 session-create work; H1's cold-switch finding), outside this lane's paths. Every lag-p99 reading ≥300 ms in every arm decomposes into that stall plus the sub-300 ms prompt-dispatch residual — none of it is slow-consumer backpressure.

## 4. The parent-ordered discriminating pair (answer 01)

## 5. Harness notes — two real G2 harness bugs found and fixed in this lane's copy (G2's originals untouched)

G2's harness (`/root/orch-ops/orchestration-scaling/g2/harness/`) was copied verbatim into `/root/orch-ops/orchestration-scaling/hb1/harness/` and amended. Two latent bugs mean G2's `G2_NODE_EXTRA_ARGS` diagnostics path never worked — future users should know:

1. **Node flags after the script path are script args.** `server-exec.sh` appended `${4:-}` after `scripts/validation-server.ts`; Node only parses flags *before* the script, so `--cpu-prof` silently reached the script (which ignores it). r4's profile was of the wrapper only. Fixed in the copy (flags precede the script).
2. **The server runs as a DETACHED child; wrapper flags never reach it, and `systemd-run` strips the caller environment.** `--cpu-prof` must ride `NODE_OPTIONS` (it is on Node's allowlist), and any env knob must be forwarded explicitly (`start-server.sh` now passes `-E HB1_CPU_PROF_DIR=…`; `server-exec.sh` merges the flags into `NODE_OPTIONS` only when requested).
3. *(Operational, from the L-pair:)* a backgrounded `A && B && C &` chain is one job — an early failure (here: `rm -rf` racing the arm's own `mkdir`) silently kills everything downstream, including the burner launch. The L-pair therefore runs the burner as a **named transient unit** (`systemd-run --unit=hb1-L-burner --collect`, same `CPUQuota`/`MemoryMax`/`Nice` containment as the answer's `--scope`) verified active before the arm and stopped by name after it — lifecycle-safe against shell races.

Other additions: `ws-subscriber-sync.mjs` (the d1-generation slow subscriber restored, per-frame sync writes, plus `--deltas-out` full-frame dump); `driver-g2.mjs` `--sub-script`/`--sub-dump` flags and a transcript snapshot before `pi-orch cleanup` (cleanup deletes the session file — the delivery assertion needs it); `analyse-cpuprofile.mjs`; `assert-delivery.mjs` (in-order/lossless assertion: strict monotonic frame sequence, deltas-before-`message_end` per message, concatenated delta text equals the transcript's final assistant message); `cpu-burner.mjs` (allocation-free 8-worker integer spin for the L-pair; an earlier draft's LCG sentinel bug made workers exit after ~4 s — the sequence is a full-period permutation, so it always reached the break).

## 8. Blind spots

1. **G2's d1 freezes remain unattributed at the mechanism level** — they cannot be re-observed on master even under synthetic 8-core load (L-pair), so no profile of them exists; G2's own logs show them as `<none>` (no span covers the WS delivery path — G2's streaming-span R4 proposal remains the instrument that would have named them).
2. **The L-pair models CPU contention, not I/O or memory pressure** — G2's busy window could have differed in kind (disk contention from other agents' suites). The residual stall being scheduling-shaped makes CPU the right first probe, but a different load type could still discriminate; that is E1-watch material, not a fix warrant.
3. **The disposable unit runs at `CPUWeight=100`/`Nice=5`** (it cannot starve production) — absolute lag numbers on it are pessimistic relative to production's weight; comparisons are arm-internal.
4. **zai's streaming arrives in ~1.2 s bursts** (provider/CDN shape; measured at the subscriber), unlike the mock's steady 25 ms cadence — real-provider arms are structurally less able to build steady-rate backpressure; r2's 17.5-min turn mitigates but does not remove this.
5. **One subscriber per subscriber-arm** (d1's shape); the G2 e3-style multi-subscriber variants were not re-run on master.
