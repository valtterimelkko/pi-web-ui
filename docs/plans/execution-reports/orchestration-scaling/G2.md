## Part 1 — Attribution: the sticky `LoopAttribution` context (fixed)

### Root cause (mechanism, verified in code and in production logs)

The loop-stall attributor singleton (`getLoopStallAttributor()`) is created lazily at the first instrumented call
after a server start — a Pi session create (`pi.service.initialize` in `PiService.createSession`, reached through
`pi.multi.create_session`), which runs inside that session's `withCorrelation({requestId, sessionId, runtime}, …)`
scope. `start()` scheduled the sampler's first tick inside that AsyncLocalStorage context, and because the sampler
**reschedules itself from inside each tick**, the whole timer chain captured that session's correlation context
permanently. The central logger reads the correlation context **at emit time** (`server/src/logging/logger.ts`,
`getCorrelationContext()`), so every later stall log line was stamped with the first session's `req=/run=/sid=`
tags — including long after that session finished, and for stalls caused by other sessions.

Production match: all stall lines since the 2026-09-30 09:55 restart carry the T1 child's
`req=req_d01879b5… run=7e867d63… sid=01a0f161…` tags (50 such lines in the 11:42:50–11:48:10 window alone,
magnitudes 58→247 ms, all `attributed to <none>`), including lines after that child finished.

### Fix (commit `12c8f777`), without dropping attribution (frozen guard respected)

- `server/src/logging/correlation.ts`: new `runOutsideCorrelation(fn)` — runs `fn` with an empty
  AsyncLocalStorage store (Node's documented undefined-store contract, passed through an explicit cast for the
  type binding). No behaviour change for existing callers.
- `server/src/observability/loop-stall-attribution.ts`:
  - the sampler chain is scheduled — and every tick runs — outside any correlation context, so no session's ids
    can stick through the chain regardless of which context first touched the singleton;
  - each span frame captures the ids of the context that entered it (`enter()`); a stall carries the innermost
    active frame's ids, rendered in the logger's suffix style (` [req=… run=… sid=… rt=… exec=…]`). Result:
    **correct** ids while a run's work is on the loop, none after the run ends. Span events are unchanged (they
    emit inside the caller's own context and were always correctly stamped).
- `docs/OBSERVABILITY.md`: the B1.2 section updated for the new stall-line format and the correlation-hygiene rule
  (touch outside owned paths, disclosed: it is the canonical doc for this module).

Attribution call sites that had to change: **none** — `enter()`/`span()`/`spanAsync()` signatures are unchanged;
all five `getLoopStallAttributor()` call sites (`pi-service.ts` ×6 spans, `multi-session-manager.ts` ×2,
`websocket/connection.ts` ×1) work unchanged. Context entry points checked (`E1` class, all `withCorrelation`
call-sites — `websocket/connection.ts:1429`, `internal-api/routes/sessions.ts` ×6, `request-logging.ts:51`): the
only long-lived self-rescheduling producer of stall lines is the sampler chain itself; span lines are emitted
synchronously inside the caller's context. No other path can stamp a finished run's ids onto stall lines.

## Part 2 — The 11:43 episode: reproduction on a disposable server

### Episode reference numbers (production, read-only)

`~/.pi-web-ui/metrics/health-metrics.jsonl`, 11:42:11→11:49:41Z: main-thread CPU 2.3→52.8 % of one core
(rising 7%→52.8% between 11:43:11 and 11:47:41, i.e. ~+46 pp over ~4.5 min), lag p99 8→433 ms (≥274 ms for
~2.5 min), activeTurns=2 throughout, heap 158–373 MB (no growth pattern). CPU fell to 5.9% within ~60–90 s of the
child's turn ending `aborted` at 11:47:54. The child's persisted partial for that turn: one 325-byte tool call,
**no thinking or text persisted**, no B3a budget event, no auto-retry logged.

### Instrument (zero quota, production never touched)

- Disposable compiled validation server from this worktree under a transient systemd unit (`CPUWeight=100`,
  `Nice=5`), T1's isolation: isolated `HOME`/`PI_CODING_AGENT_DIR`/Agent OS stub/vault/board, notifications off,
  `SESSION_DIR` unset. Real deployed extension set as byte-identical copies (B1.3-live method) for RUN-A; an
  **empty** extensions dir for RUN-B (the "extensions versus none" factor).
- Local mock OpenAI-compatible streaming provider (adapted from T1's calibrated mock; ~40 deltas/s,
  ~120 chars/s default rate), registered as the agent dir's only provider with a dummy key; per-request shape
  from a config file. No real credential existed in either run's agent dir.
- T1's sampler unchanged: every 5 s, main-thread CPU from `/proc/<pid>/task/<pid>/stat`, lag/heap/activeTurns
  from `GET /api/v1/capacity` on the disposable socket only.
- Decision rule (fixed before measuring, from the brief): a factor is the named cause when its reproduction shows
  main-thread CPU rising ≥20 pp over 5 minutes **or** lag p99 ≥200 ms, and removing only that factor removes the
  effect in the same harness. Otherwise: "not reproduced" with what was tried.

### Mechanism probe (in-process, upstream code imported read-only)

`parseStreamingJson(block.partialArgs)` runs on **every** `toolcall_delta` (upstream `pi-ai` openai-completions;
JSON.parse → full `repairJson` char loop → JSON.parse → partial-json fallback, all over the whole accumulated
string, per delta). Probe over one 64 KiB call at 4-char deltas (16,376 deltas): **18,055 ms of main-thread
CPU**, per-delta cost rising 0→1.14 ms @32 KiB→1.60 ms @64 KiB — the quadratic confirmed and quantified; at the
calibrated delta rate it integrates to the measured +10…18 pp, far below the episode's +46 pp, and B3a bounds it
at the cap (validated live twice: `budget_exceeded`, receipt terminal code, no silent overrun).

### Verdict against the fixed decision rule

**Not reproduced.** No listed factor reaches ≥+20 pp over 5 minutes with lag p99 ≥200 ms:

- long thinking stream: flat ~4% — excluded;
- long text stream: flat ~4% — excluded;
- long streamed tool-call argument: real but bounded quadratic (+10…18 pp, lag ≤4 ms), and the episode's own
  evidence excludes it (325-byte persisted args; no budget event; a budget trip logs and aborts, which did not
  happen);
- large session context (~194k tokens, episode-realistic; production's auto-compact counter measured 195,254
  tokens at the episode — the brief's "~330k tokens" is the transcript-size estimate) + streaming: flat ~4.1% —
  excluded;
- real extension set vs none: no material difference;
- no step moved lag p99 above 5 ms (baseline 2 ms); the episode saw 274–433 ms.

Consistency arithmetic (hypothesis, not a finding): every in-process per-delta path is O(1) per delta on the
thinking/text routes, so CPU% ≈ rate × constant. The measured instrument produces ~4% at ~120 chars/s; the
episode's 53% would correspond to a ~1,600 chars/s sustained provider rate through the same flat pipeline — a
provider-side burst would explain all four observations (linear rise, nothing persisted, no budget trip, fall
within seconds of the stream ending) and is invisible inside our process. This is recorded as the remaining
hypothesis; it is not testable with local instruments and motivates no code change on our side.

## Part 2b — Parent answer 01 factors (browser-subscriber fan-out; real zai turn)

### Factor (a) — browser-subscriber fan-out (RUN-C, RUN-C2, RUN-E)

Instrument: the same disposable-server harness with one additional component — real WebSocket subscribers that
log in exactly like the browser (`POST /api/auth/login`, cookie + allowed Origin at upgrade), send
`subscribe_session` + `switch_session`, and record every inbound frame (bytes, delta length, carried-message
size) plus, in debug mode, frame heads. Three subscriber generations: sync per-frame disk writes (RUN-C/C2),
then a buffered writer flushing once per second (RUN-E) — the writer change was made after d1 to remove the
subscriber's own disk behaviour as a confound.

| run | subs | subscriber reader | CPU mean/max % | lag p99 max | shed | outcome |
|---|---|---|---|---|---|---|
| c1 (RUN-C) | 1 | sync per frame | ~5 (collapsed) | alert 7,526 ms; shed at 1,655 ms; **9,330 ms stall** | yes | server never recovered before the driver gave up; host load spiked 4.4→10.33 at the same moment |
| d1 (RUN-C2) | 1 | sync per frame | 5.1 / 20.2 | **625 ms** (window ≈ 25–120 s after prompt) | yes (2,340 ms) | completed; lag then 1–2 ms for the remaining 3.5 min while the stream continued |
| e1 (RUN-E) | 1 | buffered 1/s | 4.8 / 18.2 | **110 ms** (first ~25 s only) | no | completed; then 1–2 ms |
| e2 (RUN-E, control) | 0 | — | 4.0 / 6.4 | **2 ms** | no | completed — same harness, clean |
| e3 (RUN-E, partial) | 3 | buffered | 4.9 / 8.0 | **2 ms** | no | observed ≈165 s; the driver was lost at the 17:34 turn stall (RUN_TRANSPORT_LOST fence — noted per parent); the server-side run itself completed `terminal_signal` |

Reading:

1. **The episode's CPU-rise signature never reproduced**: main-thread CPU stayed flat (~4–5%) in every
   subscriber arm. The episode rose 7→52.8%.
2. **Lag with subscribers is real but tracks the subscriber's consumption behaviour, not per-update server
   work**: the wire frames are constant (401 B; delta 3 chars; carried message 43 B — no accumulated content,
   every minute of every run), yet the sync-writer subscriber produced 625 ms p99 and a shed trip, the buffered
   subscriber 110 ms, three buffered subscribers 2 ms, and the no-subscriber control 2 ms. The lag is
   early-turn-bounded and recovers completely while the stream continues — not a growing per-update cost.
3. **The outbound governor never tripped** (no slow-client close, no queue counters): its caps bound buffered
   memory (4–16 MB), which a 401 B frame at ~40/s never approaches — the governor bounds memory, not latency.
4. The worst instance (c1) had a coincident host-load spike (4.4→10.33), so its 9.3 s collapse is
   host-amplified; the reproducible core is d1's 625 ms window.

Rule adjudication: d1 met the frozen lag threshold (625 ≥ 200 ms) with the same-harness removal control clean
(e2, 2 ms) — but the magnitude did not reproduce with a faster reader (110 ms, then 2 ms), and the episode's
dominant CPU-rise signature never appeared. Recorded verdict: **factor (a) is a real lag sensitivity worth a
robustness proposal, not the 11:43 episode cause** — production's episode child was Internal-API-driven (no
browser subscriber), consistent with the exclusion. The mechanism of the subscriber-path stall remains
unidentified (LoopAttribution shows `attributed to <none>` — no span covers the WS delivery path).

### Factor (b) — real zai streaming shape (RUN-Z)

Instrument: the disposable server's isolated agent dir with **only** the approved `zai` credential (no mock
registered, so the served route is structural; receipts show `zai/glm-5.3-flash`), thinking `high`, a
reasoning-forcing prompt, and a local tee proxy between the runtime and the provider (provider-level `baseUrl`
override in the isolated agent dir; the proxy forwards verbatim, tees per-chunk sizes and response heads, and
never stores credentials). The provider's raw stream is therefore captured on this host for the first time.

| run | subscribers | stream length | SSE bytes | chunks (est.) | chunk rate | lag p99 max | CPU mean/max % |
|---|---|---|---|---|---|---|---|
| z1 | 0 | 43.6 s | 374,895 | ~1,970 | ~45/s | 147 ms (one early window) | 4.8 / 25.2 |
| z2 | 1 | 8.7 s | 72,745 | ~380 | ~44/s | 2 ms | 4.4 / 10.4 |

Findings (the parent's questions, answered from the raw capture):

1. **zai sends true increments, never cumulative text**: every captured chunk carries a 1–3 char
   `reasoning_content` (or `content`) delta inside a ~190-byte chunk envelope (`response-first-bytes` in
   `runs/g2-ep-z/tee-chunks.logl`; subscriber-side deltas 1–3 chars at constant 400 B frames). A
   cumulative-resending provider would make per-chunk parsing O(n); zai's shape does not.
2. **Chunk rate ≈ 45/s vs the mock's calibrated 40/s** — the mock instrument's delta rate is representative;
   T1's 2.1× hotness factor bounds remain the right conservative conversion.
3. Neither arm reproduced the episode shape: CPU flat, no lag beyond one 147 ms early window (z1, no
   subscriber) — below the frozen 200 ms threshold.
4. Both turns ran shorter than the 3–5 min aim (glm-5.3-flash finished the reasoning task in 8.7–43.6 s of
   streaming). The chunk-shape conclusion is per-chunk and unaffected; the runs do not test long-duration
   real-provider behaviour (recorded as a blind spot).

### Verdict on the episode (parent answer 01, items 1–2)

**Not reproduced.** All five brief factors plus both answer-01 factors are measured; none produces the linear
CPU rise; the only ≥200 ms lag instance (d1, 625 ms) tracks subscriber consumption behaviour, is
early-turn-bounded, was not reproducible at magnitude with a faster reader, and cannot explain a CPU rise that
was not present. The known real cost on these paths remains the upstream tool-argument parse quadratic, which
B3a bounds (validated live) and which the episode's own evidence excludes. No speculative fix merged (owner
rule). The sticky-attribution fix means the next such episode names its session and code path.

### Proposal for R4 (answer 01 item 3 — not built)

Two observability additions would close the remaining diagnosis gaps; both are small and provider-free:

1. **A streaming-path span.** Wrap the per-delta funnel (`handleAgentEvent`'s projected-update delivery, or a
   span around the SDK event subscription callback) so LoopAttribution can name the streaming path instead of
   `<none>`. Today a stall caused purely by streaming delivery reports no span; G2's episode evidence would
   have been conclusive with one.
2. **A per-provider delta/chunk-rate counter in the A2 telemetry** (chunks/s and bytes/s per provider on
   `/capacity`, ring-buffered like the lag series). The zai capture proves the counter is cheap to compute
   provider-side; it would have shown immediately whether the 11:43 episode was a provider burst (rate
   ×1,600-ish) or something else, and it turns "provider degraded" from a story into a number. Triage note:
   the same counter would have flagged T1's wake-loop artefact class early.

Both are follow-up work for the parent to allocate (observability lane or E2); no code for either exists in
this lane's commits.

## Blind spots (what this evidence does NOT see)

1. **Mock fidelity:** the calibrated rate (~40 deltas/s, ~120 chars/s) is T1's text-stream calibration; the real
   glm-5.3-flash thinking/args delta rates are unmeasurable from transcripts. The 2.1× mock-hotness factor was
   measured at one concurrency for text and applied uniformly.
2. **Single run per factor:** one run per instrument (as T1); step means carry run-to-run variance (the two
   independent 80k runs differ by 0.2 pp — small, but n=1 each).
3. **The second production turn is unknowable:** turns=2 during the episode; the other session's stream content,
   rate and even identity are not recoverable from what production recorded. My harness ran one turn at a time;
   a two-turn interaction was not modelled (the fall within seconds of one child ending argues against the second
   turn being the driver).
4. **Provider-side behaviour is invisible:** zai's server-side streaming (bursting, throttling, retry semantics)
   cannot be observed from this host; the burst hypothesis is consistent with all evidence but unproven.
5. **Zero-browser assumption:** the harness sessions had no WebSocket subscribers; a browser-heavy fan-out during
   streaming adds per-delta broadcast work (delta-slimmed since 2026-09-05, but not re-measured here).
6. **Attribution fix coverage:** the fix makes the *next* episode attributable (correct ids while a run's spans
   are active; none after; span labels + `blockedBy` name the blocker). The streaming delta path itself is not
   wrapped in a span, so a stall caused purely by provider-rate flooding will still report `<none>` — visible as
   such, but not named. Adding a streaming span + a provider delta-rate counter would close this; it is new
   observability work, proposed to the parent, not built here (no unvalidated fixes; no scope grab).
