   - **Version guard:** `INTERNAL_API_CONTRACT_VERSION`'s `major.minor` must
     stay `1.58` unless an exception row names the version that moved. Fails on
     a simulated `1.59.0` (and `2.0.0`) with no row; passes `1.58.1` with no
     row; passes `1.59.0` when a row names `1.59`.
   - **Snapshot shape guard:** the enforced baseline fingerprint is the SHA-256
     of the parsed client snapshot at 1.58.0 with the top-level `contractVersion`
     field removed and object keys recursively sorted —
     `851a1545ab6f15cf2d2f1d26c3a59567b5bc17e95e8d8c6e867a3ce40dd4c7e9`
     (full-file SHA-256 at 1.58.0:
     `fab83d8b2c237d0f8d43733dbeff60fb45c2ee690cfe7ca2b1cc044da4dc5fec`,
     informational). Any other body change — a properly **regenerated** snapshot
     whose route set, type set, error-code table, zod schemas, fields or source
     lists differ from the 1.58.0 baseline — fails unless an exception row names
     the current `major.minor`. This closes the gap the existing
     `client-snapshot-drift.test.ts` leaves open (it only catches a schema
     change *without* regeneration). A patch bump passes because stripping
     `contractVersion` makes a `1.58.x` regeneration fingerprint identically to
     the baseline.
   - **Doc anchor:** the test parses the window section and fails if the
     declaration, its version/date, or the "set by the owner at R3 /
     open-ended" statement is removed or altered. The exception-table parser
     tolerates an empty table (the current state) and is covered by a
     synthetic-doc test with one row.
   - Failure messages enumerate what moved (added/removed routes and types by
     name; "field, error code, zod schema or source-file change" when sets are
     unchanged but the body moved).

## Design decisions

- **Fingerprint = `contractVersion`-stripped canonical shape, not the raw file
  hash.** The window explicitly allows patch bumps, and any version bump
  regenerates the snapshot (the drift test pins `contractVersion` in the
  snapshot to the code constant). Stripping only `contractVersion` makes patch
  bumps pass by construction while every other body change trips. The raw
  1.58.0 file hash is recorded in the doc section and the helper for reference.
- **Any `major.minor` move away from `1.58` needs a row** (not only increases):
  strictly stronger than "moves past 1.58", and a downgrade is also
  client-observable. RED receipt shows the specified `1.59.0` failure.
- **Guard logic as a pure helper** colocated with the test: the simulated-bump
  tests run against in-memory clones of the committed snapshot — cheap
  (787 ms file), deterministic, no fs writes, and the live guards stay one
  assertion each.
- **Exception table columns** exactly as the brief: date, owner decision, what,
  version; the parser requires all four and tolerates zero rows.
- **Doc section wording kept declarative** (no JSON blocks) so the existing
  version-integrity drift test's `contractVersion`-example check is unaffected.

## Blind spots (what this mechanism does NOT see — for §1.1 adjudication)

1. **Wire-visible changes with no snapshot/constant/doc surface.** A behaviour
   or default change inside server code that changes no schema, route, type,
   error code or snapshot byte — and gets no bump — passes every guard, exactly
   as before C6. No test can prove "this diff is wire-visible, so bump"; that
   stays a human judgement at review (the same class of miss as the 2026-09-15
   watchdog incident).
2. **New SSE event types.** Event types are not in the client snapshot; a new
   event type with no type/route surface change passes the shape guard. Only an
   exception row (or a response-type change) records it.
3. **Exception rows are trusted, not interpreted.** The guard accepts any
   snapshot shape once a row names the current `major.minor`; it cannot check
   that the row's "What" column actually covers the diff.
4. **Parser is wording-anchored** to this section's headings and bolded
   version/date. Rewording the section breaks the parse — which fails the test
   loudly (safe direction), but the section is not free-form.
5. **No expiry enforcement.** The window is open-ended until the owner sets its
   length at R3; the guard has no notion of a closing date. When the owner sets
   a length, the guard (and this doc section) need a follow-up update.
6. **After an exception lands**, the baseline stays 1.58.0 by design — every
   later windowed change still needs its own row. The parent may prefer to
   re-baseline at R3 together with setting the length.
