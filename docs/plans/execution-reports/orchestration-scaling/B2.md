# B2 — heap- and lag-aware admission, disposal always available

**Status:** implemented and live-proven on a disposable server; awaiting independent review, parent verification, the Agent OS mirror update and the owner-approved production check.
**Lane:** `b2` · **Worktree:** `/root/.worktrees/orch-scaling/b2-pi-web-ui` · **Branch:** `orch/b2` (base master `08276a86`) · **Contract:** `1.49.0`

## What shipped

- **`heap_pressure`** (`server/src/internal-api/admission-controller.ts`). Projected V8 heap = `used_heap_size` + `reservedHeapBytesPerTurn` × (active P2/P3 turns + 1), read from `v8.getHeapStatistics()`, compared with `heapPressureFraction` × `heap_size_limit`. The refusal latches at ≥ 0.75 and releases only strictly below 0.65 (hysteresis). An unknown limit fails open.
- **`event_loop_lag`**. A2 readings feed admission through a read-only `HealthTelemetry.onReading` listener (`server/src/observability/health-telemetry.ts`; sampling and alerting unchanged). Two consecutive readings with p99 ≥ 300 ms latch the refusal. Only a reading with p99 strictly below the recovery mark releases it (default: half the trigger, 150 ms). Readings with no samples are ignored. A latched state whose last reading is older than 180 s fails open and reports `stale: true`.
- **B4 seam**, implemented verbatim: the union includes `'draining'`, `setDraining`/`getDraining` sit directly after the constructor, and the P2/P3 branch starts with `if (this.drainingState) return 'draining';`. `/capacity` exposes `draining`.
- **Admission acts at create as well as prompt** (`routes/sessions.ts`). `POST /sessions`, each `POST /sessions/batch` entry and `POST /sessions/:id/transfer` with `createNew` call `assertCreateAdmissible`. Every pressure reason (`memory_pressure`, `host_memory_pressure`, `pid_pressure`, `heap_pressure`, `event_loop_lag`) and `draining` refuse creates. Turn-slot limits never do, because a create holds no turn.
- **One refusal shape.** `sendAdmissionRefusal` returns `ADMISSION_CAPACITY_EXHAUSTED` + `reason` + `retryAfterSeconds` + a `Retry-After` header. Status is `429` for `global_limit`/`runtime_limit` and `503` for everything else. This also fixes the Command Code prompt path, which answered `429` even under pressure. `heap_pressure` and `event_loop_lag` carry `Retry-After: 30` (one A2 interval).
- **Disposal always available.** `DELETE /sessions/:id` no longer goes through `wrapControl`'s `CONTROL_CRITICAL` floor. It runs in its own bounded disposal lane (4 concurrent, 32 queued), so neither the critical floor nor a saturated control lane can refuse it. `POST /sessions/:id/abort` is floor-exempt too, but stays on the control lane (an existing test pins that). Other control keeps the floor. The Internal API has no batch-delete or cleanup route; DELETE is the complete disposal path ("explicit session DELETE overrides retention").
- **`GET /api/v1/capacity`** adds `heap`, `eventLoopLag`, `draining` and `disposalLane`. Top-level `reason` now uses the same precedence as a P2 acquire.
- **Configuration** (`server/src/config.ts` → `server/src/index.ts` → `resolveInternalApiAdmissionOptions`): `INTERNAL_API_ADMISSION_HEAP_PRESSURE_FRACTION`, `_HEAP_RECOVERY_FRACTION`, `_HEAP_RESERVED_MB_PER_TURN`, `_LAG_P99_MS` (the single lag knob), `_LAG_RECOVERY_MS`, `_LAG_SUSTAINED_READINGS`. Invalid values fail startup, like the existing admission knobs.
- **Validation-only pressure file** (`createValidationPressureOverride`). `INTERNAL_API_ADMISSION_TEST_PRESSURE_FILE` is honoured only with `PI_WEB_UI_VALIDATION_MODE=true`. It is re-read on each evaluation and can override `heapUsedBytes` and/or the observed lag p99. Production never enables validation mode.
- **Docs:** `docs/INTERNAL-API.md` (capacity section, heap/lag gates, create gate, disposal, env knobs, error table) and `docs/INTERNAL-API-CONTRACT.md` (1.49.0 changelog, error row, invariant 10).

## Default choices and why

| Knob | Default | Evidence and reasoning |
|---|---|---|
| heap pressure fraction | 0.75 of `heap_size_limit` | The cap stays at 4 GiB (owner, 2026-09-28). The B1 confirmation soak puts the fixed build's floor at ~200 MB post-GC with a 242 MB peak. 0.75 ≈ 3 GiB trips an order of magnitude above that floor, so ordinary operation never refuses, and it still leaves ~1 GiB for in-flight turns and a full mark-compact before the OOM. |
| heap recovery fraction | 0.65 | ≈ 2.6 GiB. Wide enough that garbage-driven oscillation of `used_heap_size` around the trigger cannot flap admission. |
| reserved heap per turn | 64 MiB | Projects growth that has not happened yet. At the production ceiling (`maxActiveTurns` 6 by default) the reservation is at most 384 MiB, inside the 1 GiB band. |
| lag trigger | 300 ms p99, 2 consecutive A2 readings | Per the brief and B1.2 §"Proposed B2 threshold": the pre-fix build crosses it in every load window; the post-fix build never does. |
| lag recovery | trigger / 2 = 150 ms | Per the brief. B1.2's final section proposed 200 ms, because steady-state p99 reached 162 ms in `b13-final`. The parent can set `INTERNAL_API_ADMISSION_LAG_RECOVERY_MS=200` without a code change. The trigger remains one knob and the derived recovery follows it. |
| Retry-After (heap/lag) | 30 s | One A2 interval. The lag state cannot change sooner. |
| lag staleness | 180 s | Six A2 readings. A dead sampler must not refuse API work forever. |

## Residual risks

- `used_heap_size` includes garbage not yet collected, so projected heap overstates live heap between collections. This matters only near the 3 GiB trigger, where caution is the point.
- The lag gate depends on A2 telemetry running (`OBSERVABILITY_METRICS_ENABLED` not `false`). Without readings it is inert (`telemetryAvailable: false`), not failing closed.
- At the 30 s production cadence, a refusal needs about 60 s of sustained lag. Short spikes pass by design, and a single runaway turn is B3's concern, not B2's.
- A flood of more than 36 concurrent DELETEs can still get `CONTROL_LANE_FULL` from the disposal lane. This is bounded by design.
- If the sampler stops while lag is latched, admission resumes after 180 s (fail-open by design).
- P0 browser (WebSocket) work is outside Internal API admission, as before.
