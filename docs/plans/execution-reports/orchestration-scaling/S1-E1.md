## Part 1 — weekly refresh restart budget (plan §6 small item, B4 residual)

### What shipped

The weekly Command Code refresh called `restart-pi-web-ui.sh` with a flat 60 000 ms timeout. The wrapper can spend drain (default 20 s) + HTTP slack (default 10 s) deciding, and `systemctl restart` then blocks for the unit's stop (`TimeoutStopSec=30` in `deploy/systemd/pi-web-ui.service`) plus the start — so a slow stop could outlive the call, fail the refresh **after the catalogue was already committed**, and leave the restart state uncertain. Chosen fix: **raise the job timeout above drain + slack + stop, with an explicit start margin** (the brief's first option). Justification for not choosing the non-blocking restart: a non-blocking restart would have to change how `restart-production.sh` invokes systemctl — excluded by this lane's negative exclusions (B4.1 internals) — and would lose the exit-code semantics the job relies on to distinguish restart success from a "refusing restart" deferral; the job is a weekly 04:45 maintenance window, so a longer synchronous budget costs nothing.

- `scripts/command-code-weekly-refresh.ts`: named, exported budget parts — `RESTART_DRAIN_BUDGET_SECONDS=20` (the wrapper's `PI_WEB_UI_JOB_DRAIN_TIMEOUT_SECONDS` default), `RESTART_DRAIN_HTTP_SLACK_SECONDS=10` (its `PI_WEB_UI_DRAIN_HTTP_SLACK_SECONDS` default), `UNIT_STOP_TIMEOUT_SECONDS=30` (the unit's `TimeoutStopSec`), `RESTART_START_MARGIN_SECONDS=90` (Type=notify readiness margin, systemd's default `TimeoutStartSec`) — and `RESTART_JOB_BUDGET_MS` (150 000) now passed as the restart call's `timeoutMs`.
- `scripts/restart-pi-web-ui.sh`: header wording only (budget description + help range widened `2,42p` → `2,46p` to match the longer header). No constant changed: the fix is at the caller.
- `docs/COMMAND-CODE-INTEGRATION.md` refresh section: documents the budget arithmetic and the drift-pin tests.

## Blind spots (what this evidence does NOT see, per plan §4)

- The proof simulates the slow stop with a fake `systemctl` seam against a **transient disposable unit**, not against `pi-web-ui.service` itself: it proves the budget arithmetic and the wrapper/restart-path wiring, not production's own stop duration distribution. Production `TimeoutStopSec=30` bounds the real stop; the 90 s start margin is assumed from systemd's default `TimeoutStartSec`, not measured on this host's boot time (the disposable restarts booted in seconds).
- The unit-test drift pins read the repo copies (`deploy/systemd/pi-web-ui.service`, `scripts/restart-pi-web-ui.sh`). If the host's installed unit diverges from the repo copy (installed copies are host-specific per the unit header), the budget constant would not know.
- `runProcess`'s timer SIGKILLs only the direct child (the wrapper); as run B showed, grandchildren can survive and complete the restart. Under the NEW budget this matters far less (the call only times out past 150 s), but the caller-timeout-kill semantics remain "kill the wrapper, orphan the rest" — unchanged by this lane.
- The ledger's Table A statuses reflect plan steps shipped as of this lane's base (`f29fc38f`); the unmerged follow-up lanes (b41 correction 01 etc.) may already close more of it by the time the parent merges. The ledger flags exactly one such case (the two orch/b41 test files).
- The E1 ledger records classes and tests; it does not re-run the Jev evaluation, and E2's final re-measure (not this lane) is the instrument for recurrence numbers over time.
