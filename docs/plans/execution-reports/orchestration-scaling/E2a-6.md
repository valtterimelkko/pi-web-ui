## 1. Method and decision rules

**Sources.** `~/.pi-web-ui/run-receipts/*.json` (rolling store, 1,003 files at generation;
oldest acceptedAt 2026-09-24T13:47:40Z — the whole window is covered by the store), Pi
session transcripts under `~/.pi/agent/sessions/` (`goal_engine` custom entries — the pi
goal engine's per-generation state records), `~/.pi-web-ui/antigravity-sessions/goal-control/*.json`
(the antigravity goal manager's per-goal control records), `~/.pi-web-ui/watches/` (parent
watch ledgers), `~/.pi-web-ui/session-registry.json` (fallback for goal routes only),
`journalctl -u pi-web-ui.service` (drain/restart reconciliation lines), and the programme's
own records under `/root/orch-ops/orchestration-scaling/` (`create.json` / `goal-*.json`
discovered **recursively**, including `e2/<lane>/`, plus `retention.ownerId` values starting
`orch-` → programme; `STATE-j.md` / `STATE-hwave.md` / `STATE-interim-r4.md` /
`h2s/status.md` where a classification needed the parent's contemporaneous record).

**Frozen snapshot (item 1).** `--as-of 2026-10-02T19:00:00Z`: receipts are included only if
their terminal (or, for the non-terminal note, accepted) time is ≤ the cut; a receipt that
turned terminal after the cut is treated as not-yet-terminal at the cut and excluded.
Transcript `goal_engine` entries, antigravity goal-control updates and watch firings are
likewise filtered to ≤ the cut. The stamp is written into `out/tables.md` (header), every
`out/items.csv` row (`as_of` column) and this report. **Reproducibility (shown):** two
back-to-back runs with the same `--as-of` produced byte-identical `out/items.csv` and
`out/journal-restarts-window.txt`, and `out/tables.md` identical except its
"generated <now>" provenance stamp (diff shown in the hand-back). What a live store can
still change for a past time, and how it is handled: (a) receipts that turn terminal after
the cut — excluded, by design, so the terminal count is the count as of the cut (a receipt
accepted 18:47Z that terminated 19:03Z is invisible here); (b) rolling-receipt rotation and
transcript pruning can *remove* old evidence, so a much later re-run could see fewer items —
not preventable read-only; at generation the store reaches back to 2026-09-24, far past the
window; (c) the session registry is live and is used only as a route fallback after the
immutable receipt records, so a pruned registry cannot change a route that a receipt already
fixed.

**Population.**
- *Runs:* every in-window receipt with a non-success terminal state — 40 items (37 `failed`,
  3 `cancelled`) — anchored on the **44 `RUNTIME_ERROR` receipts** the store held on
  2026-10-02: 37 fall in the window, 7 predate it (2026-09-27/28; classified as pre-window
  context in Table 6, all `unknown` — empty `finalText`, transcripts pruned). The store's
  other terminal codes (`NEVER_STARTED`, `RUN_TRANSPORT_LOST`, `RUN_BUDGET_EXCEEDED`) do not
  occur anywhere in the store (full status×errorCode enumeration in §5). Receipts
  non-terminal at the cut are excluded and listed as such (at this cut: 0 — the six
  queued/started receipts seen in earlier live snapshots all carried event times handled by
  the cut rule).
- *Goals:* one item per goal **generation** (registration → final state) visible in the
  window and at or before the cut: 53 pi goal-engine generations (282 transcripts scanned) +
  5 antigravity goal-control goals = 58; of these 53 ended in-window (46 achieved, 7
  not-achieved) and 5 are still running at the cut (the E2 lanes themselves, this wave). A
  6th antigravity goal (a 2026-09-09 smoke) predates the window.
- *Denominators:* 162 terminal receipts in-window (122 completed + 40 non-success); 53 goal
  ends in-window. All run counts are **receipt-terminal outcomes**; a provider abort inside
  a goal turn can sit behind a `completed` receipt (see §8 and §9) — the j6 14:45Z case is
  counted in the goal table, not the run table.

**Rules (coded in `classify.py`, applied mechanically):**
- `provider-transient` — receipt `finalText` matches the antigravity provider error shapes
  (`agy ERROR … INTERNAL (code 500) / UNAVAILABLE (code 503) / high traffic / No capacity`);
  or `finalText` is "The agent did not return a reply (timeout|stall)" on the antigravity
  route (the agy goal manager itself files no-reply stops as `provider error (strike N/3)`
  — observed verbatim in `goal-control/217b0943….json`); or a pi goal was `paused` with no
  recorded reason and the transcript holds a provider abort marker ("Request was aborted")
  within 30 min before the pause (the j6 case, corroborated by STATE-j line 103). There is
  **no blanket antigravity fallback**: any other antigravity `RUNTIME_ERROR` is `unknown`
  unless a recorded provider-error signal exists (01-correction item 5; negative test in
  `scripts/test_classify.py`).
- `runtime-transient` — `errorCode=ADMISSION_CAPACITY_EXHAUSTED` (admission control refused
  the run before dispatch on host session capacity; a retry would clear it; one of the two
  in-window items was followed 71 s later by a completed retry on the same session);
  `TURN_STALLED` (pre-window context only).
- `restart` — `SERVER_RESTART` interruption or a restart boundary under the item
  (pre-window context only; see §4 — zero in-window).
- `child-error` — pi goal `paused` with `lastRunClassification=suspect` and
  `lastRunReason` "completion rejected: verification rejected completion" (the child claimed
  completion without producing the verified artefact); `GOAL_ACTION_NOT_APPLIED` (pre-window).
- `parent-action` — a receipt `cancelled` in the same second as its session's goal-control
  record flipping to `cleared`; an antigravity goal-control `status=cleared`; a pi goal
  paused with a recorded supervision `pauseReason`.
- `unknown` — evidence insufficient (kept honest; each instance says what is missing).

**Origin split (item 3):** session ids mapped through `orchestration-scaling/**/create.json`
and `**/goal-*.json` discovered recursively (`programme:<lane>`; nested `e2/<lane>/` records
included; a session referenced by several lanes maps to `programme:laneA+laneB`) and
`agent-os-gaps/*/create.json` (`other-programme:…`); `retention.ownerId` values starting
`orch-` are registered as programme evidence (`origin_from_owner`); everything else is
`other`. Route = runtime / **exact served model selector** (item 2).

what that route needs is the opposite of another continue (a stop/strike rule — the manager
burned 27 runs into a dead route, a finding the H-wave parent recorded). Two qualifications

inside a goal turn can sit behind a `completed` receipt (the j6 14:45Z case, which is
counted in the goal table, not the run table) — and the goal denominator covers **observed

turn-level "continue once" would have helped are **real but rare on the target route** — one
clean case in 53 goal ends and 162 terminal runs — so wave K is a small, cheap improvement
rather than a decisive one; its main value is retiring the H2-item-7 class, and it must not
be extended to blind retries into sustained provider outages (the h2s case), where the
manager needs a stop/strike rule rather than one more continue.

## 9. Coverage limits, blind spots, reproducibility

- **Rolling receipt store:** holds ~1,000 receipts back to 2026-09-24T13:47Z; the window is
  fully inside coverage, but receipts older than that are gone (irrelevant here). The store
  is live: counts are frozen at the `--as-of` cut (2026-10-02T19:00:00Z); receipts that
  turned terminal after the cut are excluded by design (a receipt accepted 18:47Z that
  terminated 19:03Z is invisible at this cut), so the cut's terminal count is a lower bound
  on what had actually happened by later reading times.
- **Reproducibility (item 1):** two runs at the same `--as-of` produced byte-identical
  `items.csv` and journal extract, and `tables.md` identical except the "generated" stamp.
  Residual nondeterminism is shrinkage-only: rolling-receipt rotation or transcript pruning
  could make a later re-run see *fewer* items; neither can invent items. The session
  registry (live) is only a route fallback after immutable receipt records.
- **Transcript pruning:** only 98 of the in-window receipt sessions had transcripts on disk
  at the first live scan; classification stands on receipts (self-sufficient: status,
  errorCode, finalText), goal-control records and parent STATE files; transcript-tail
  judgements were possible only where transcripts survive (noted per item in §3).
- **Goal ends are observable only for Pi (transcript goal_engine entries) and antigravity
  (goal-control); every goal count in this report is scoped to those observed records**
  (01-correction item 6a). Claude/opencode runtimes expose no goal store to this method, and
  this report does not claim their goal activity is zero — only that none was observable.
  In the window every receipt is pi or antigravity, so the observed-records scope covers all
  receipt-backed activity.
- **Run figures are receipt-terminal outcomes** (item 6b): "completed" means the receipt
  closed `completed`; a provider abort inside a goal turn can sit behind a `completed`
  receipt (j6 14:45Z — abort, then paused goal, then a fresh `completed` prompt receipt).
  The j6 case is kept in the goal count.
- **The h2s replacement goal** (pi session `01a0f8de…`, started 19:10Z Oct 1 — after the
  cut's window content but within it): transcript pruned, so its goal end state is not
  directly observable; its 3 receipts are all `completed` and h2s/status.md records lane
  completion 20:02Z plus correction rounds to 21:02Z. Counted in neither goal success nor
  failure.
- **Watch ledgers contributed nothing:** zero `goal_end`/`goal_state` firings at or before
  the cut (the running E2 watches are armed for goals still in flight; earlier waves'
  watches were not goal-armed). The goal-end cross-check therefore rests on transcripts +
  goal-control + the parents' STATE records.
- **The j6 attribution rule** (pause + abort marker ≤30 min) is calibrated on one case,
  corroborated by STATE-j line 103 ("provider 'Request was aborted' mid-turn … H2 item 7
  recurrence"); the pi-orch-side record the parent saw ("pausedReason error") is not in the
  transcript entry itself.
