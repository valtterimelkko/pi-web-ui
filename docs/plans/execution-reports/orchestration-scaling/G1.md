Lane `g1`, wave 4 (R3 follow-up). Worktree: an isolated execution worktree of `pi-orch`,
branch `orch/g1` (from `pi-orch` main `fc1c1cf`). Not pushed (lane branch; the

## What was built

- `src/route-limits.ts` — pure decision logic: `DEFAULT_ROUTE_LIMITS`
  (`zai/glm-5.3-flash: 5`, everything else unlimited), `resolveRouteLimits`
  (defaults ← `PI_ORCH_ROUTE_LIMITS` JSON ← per-call overrides; malformed map
  throws `RouteLimitsConfigError`; 0 = unlimited), `routeOfSession`
  (`modelSelector ?? model`), `liveReason` (busy → goal `running`/`wrapping_up`
  → nonterminal last receipt; settled children never count),
  `RouteLimitError`, `RouteLimitWaitDeadlineError`.
- `src/spawn-ledger.ts` — bare-CLI spawn ledger (`PI_ORCH_SPAWN_LEDGER`,
  default `~/.pi-orch/spawn-ledger.json`): successful spawns record
  `{sessionId, route, ownerId, at}`; owner-based counting re-checks each entry
  against the live sessions list and prunes entries whose session is gone.
  Written only when the caller has no parent identity (identity counting is
  server-authoritative via `GET /sessions?parent=`).
- `src/client.ts` — the gate: `spawn` refuses BEFORE creating anything
  (`ROUTE_LIMIT_EXCEEDED`, naming the live children and why each is live), or
  with `waitForSlotMs` waits via the existing watch-based `waitMany` (mode
  `any`, no polling, no sleep), re-counting after each settle;
  `prompt` applies the same gate only when it would START a new turn on an
  idle child of a limited route (a prompt to a live child queues after its
  current turn and cannot raise route concurrency; `steer` never gated).
- `src/cli.ts` — repeatable `--route-limit 'SEL=N|unlimited'` (validated
  before the client factory runs; flags win over the env), `--wait-for-slot S`
  (seconds → `waitForSlotMs`), exit-code mapping, help rows.
- `src/exit-codes.ts` — new **25 `ROUTE_LIMIT`**; `ROUTE_LIMIT_WAIT_DEADLINE`
  maps to the existing **3 `DEADLINE`** (the brief's "deadline code").
- Docs: README (new "Per-route child concurrency" section, environment table
  rows, exit-code row 25, spawn flag), `AGENTS.md`/`CLAUDE.md` (byte-identical
  pair, exit-code additions line), help text.

## Definition-of-victory decisions (recorded)

- **Prompt gating is applied** (needed for correctness: a prompt to an idle
  child of a limited route adds one concurrent generation the spawn gate never
  sees — e.g. children created before the cap was reached). Refuse-only; no
  `--wait-for-slot` on prompt (spawn is the fan-out entry point).
- **Counting key**: the caller's session identity first
  (`GET /sessions?parent=`, authoritative, covers every process of that
  parent); a bare-CLI caller counts by its `--owner` retention owner through
  the local ledger; with neither, warn once (`ROUTE_LIMIT_UNCOUNTED`) and
  proceed — the brief's rule. A parent identity the server does not know
  (404) also warns once and proceeds, loudly, by name.
- **Route attribution**: exact selector string (`modelSelector ?? model`).
  Children spawned without `--model-selector` carry no route on record and are
  never counted against any limit (documented; the public docs recommend an
  explicit selector wherever the cap matters).
- **Over-limit wait**: when every live child carries an unremovable foreign
  watch there is nothing watchable to wait for — the client refuses
  immediately with the normal over-limit error instead of burning the
  deadline.

## Blind spots (explicit, for plan §1.1 adjudication)

- **Counting lags the truth by one request round-trip.** Two racing spawns
  from the same parent can both observe `count < limit` and both proceed
  (the gate is advisory, not admission control; the server remains the only
  hard cap — its own admission controller is untouched).
  CORRECTION 01 item 1 narrows this: the count→create span is now
  serialised per (caller, route) with a local lock file, so two CONCURRENT
  spawns on one host can no longer both create; the residual is cross-host
  racing and the advisory (non-admission) nature of the cap.
- **The ledger is per-host and merge-on-write.** Bare-CLI owner counting does
  not span machines, and two simultaneous bare-CLI spawns can lose one ledger
  entry (last writer wins). Identity-based counting has neither limitation.
- **Children without a model selector are invisible to route counting**
  (server surfaces no selector for them). CORRECTION 01 (accepted finding):
  documented as a residual, with a README line ("caps apply only to spawns
  that name `--model-selector`") and a one-time stderr warning when caps are
  configured and a selector-less spawn is made; the orchestration skill's
  routing discipline requires an explicit live-discovered selector on every
  dispatch anyway.
- **The route key is the exact selector string.** If a server resolved a
  selector to a different concrete id and surfaced only that, the count could
  miss such children; on the observed server the applied selector is what
  `GET /sessions` surfaces (live proof: `served routes from receipts` match).
- **`prompt`-side gate counts by identity only** (a bare CLI `prompt` has no
  `--owner` to count by): bare-CLI callers get the spawn-side gate and the
  warn-once path on prompts. The realistic orchestration loop spawns and
  prompts from the same owner context, so the front door is covered.
- **`steer` and prompts to live children are never gated** (they cannot raise
  route concurrency); a burst of `follow_up`s to distinct idle children is
  gated per prompt.
- **Client-side only**: the server cannot enforce a route limit for callers
  not using `pi-orch`. (The plan deliberately scopes G1 to the parent client;
  a server-side per-route admission cap would be a wire change, which the C6
  window forbids without a question.)
- The stale-identity warn-and-proceed path (wrong `PI_SESSION_ID`) was
  exercised live only by accident (run 1) — it is now a documented, observed
  behaviour, but its "proceed" is unbounded by design.

## Residual risks

- A malicious/buggy co-tenant on the same host could delete or edit another
  user's ledger file (it lives under `$HOME`); impact is a miscounted advisory
  cap, nothing more.
- The defaults encode today's measurement (zai ≈ 5). If the provider improves,
  the env/flag override adjusts without a code change.
- The gate adds one `GET /sessions?…` + per-candidate goal/evidence reads per
  gated call (bounded 4-way parallel, few children in practice); on a server
  with a huge registry the unfiltered bare-CLI list is O(registry) — the same
  cost `status` already pays.
