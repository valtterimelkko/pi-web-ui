## 1. Question and instrument

T1 attributed ~480 ms of main-thread time per Pi session create to `pi.session.resource_loader` and named
session create / extension loading the largest attributed per-child main-thread cost. G4's brief: measure a
create split into its parts on a disposable server with the **real** extension set, cover warm (same cwd), cold
(fresh cwd) and first-create-after-boot, name the top costs, and apply the fixed decision rule — propose a change
only if projected to cut the median main-thread create time by ≥ 30 % on the warm or cold path while keeping every
B1.3 isolation guarantee and needing no upstream change.

Method (identical instrument for any future re-measure):

- **Server:** disposable compiled validation server from this worktree under a transient systemd scope
  (`CPUWeight=100`; `nice -n 10` inside the unit — this host's `systemd-run` rejects `Nice=`), launched in service
  mode with the environment pinned inside the unit (`NODE_ENV=development`; see §7), the same isolation envelope as
  T1/B1.3-live: isolated Pi agent dir, fake `HOME`, Agent OS stub with redirected board/vault state, notifications
  disabled, watch-wake pointed at the disposable socket, `SESSION_DIR` left to the validation-env builder,
  heap cap at production parity (`--max-old-space-size=4096`).
- **Agent dir = the real production resource set**, deliberately wider than T1's: the 16 deployed extensions as
  byte-identical copies (symlinked extensions are excluded from the factory cache, so copies are the only faithful
  setup), **plus the real skills corpus — 201 `SKILL.md` files, 148 MB tree — as a real copy**, plus the real
  prompts, global instructions file and settings (no credentials in any of these), plus a single approved-provider
  credential set (zai) via the T1 harness's filtered writer. T1's isolated dir had **no skills**, so T1's
  per-create attribution excluded what this run shows to be the largest single item. No prompts are sent: a create
  needs no model call, and the run makes none.
- **Load:** sequential `POST /api/v1/sessions` (`runtime: "pi"`) + `DELETE` over the disposable server's unix
  socket, one session at a time (create → measure → dispose). Clean pass (no profiler) and profiled pass on
  separate boots with identical env.
- **Measures:** client wall ms per create and delete; server **main-thread** CPU per phase
  (`/proc/<pid>/task/<pid>/stat` utime+stime delta); CPU profiles via the inspector `Profiler` domain around each
  profiled phase (200 µs sampling), aggregated by self- and inclusive-time scripts; `[LoopAttribution]` span and
  stall lines from the server log.

- Server-side `pi.session.resource_loader` spans (rate-limited log sample, n=25 across both passes):
  min 199 / **p50 248** / p90 297 / max 305 ms; stalls log as
  `pi.multi.create_session blocked by pi.session.resource_loader` — T1's attribution class, confirmed.
- **Warm ≈ cold** (524 vs 520 ms): after B1.2b/B1.3 the remaining create cost is **cwd-independent**, and the
  uncached `subagent` re-import adds no measurable cold penalty on this instrument.
- **Two baselines (correction from the parent's answer, verified in code):** the driver is a *headerless raw
  caller*, so every create ran C5's peer-credential origin resolution (`scanPeerOwners`, ~114 ms — see §3).
  Orchestrated creates (`pi-orch` sends `X-Parent-Session` whenever the caller has a session identity) short-circuit
  that scan (`linkChildFromRequest` resolves the explicit parent before the peer resolver is consulted), so the
  **orchestrated baseline is ≈ 410 ms** main-thread per create and the headerless baseline is ≈ 524 ms. Both are
  stated; the skills walk is ≈ 47 % of the orchestrated baseline and ≈ 37 % of the headerless one.

## 3. Attribution (CPU profile, per-create = inclusive ÷ 30)

| Cost | warm ms/create | cold ms/create | What it is |

Reconciliation: skills-related work (the discovery walks inside `resolve` ≈ 107 ms plus `loadSkills` ≈ 87–95 ms)
≈ **195 ms/create ≈ 47 %** of the ≈ 410 ms orchestrated baseline (≈ 37 % of the headerless 524 ms);
`scanPeerOwners` ≈ **114 ms ≈ 22 %** of the headerless baseline (0 for orchestrated callers). Neither shares
mutable state across sessions — both are pure per-create reads/scans.

## 4. Decision-rule verdict

- **A. Process-level skills-resource cache** (fingerprint the skills tree, reuse resolved user-scope skill
  resources across sessions — the audit shape of the B1.2b extension-factory cache). Projected −172…−218 ms
  ≈ **33–42 % of the headerless baseline; ≈ 47 % of the orchestrated baseline**, on warm AND cold
  (cwd-independent). **Blocked on the seam, not the design:** `DefaultPackageManagerOptions` is
  `{cwd, agentDir, settingsManager}` (not injectable, not configurable); `resolve()` runs
  `addAutoDiscoveredResources` unconditionally; the loader's `noSkills` option still runs `loadSkills` whenever
  `resolve()` returned skill paths (i.e. always in practice); `skillsOverride` transforms *after* the walk and
  reads; the resolved skill list is loader-internal. The only upstream-free variant — a full server-side
  `ResourceLoader` reimplementation — was rejected: it would reimplement parity-critical SDK behaviour and put the
  B1.3 isolation guarantees at risk for a cost lane. **→ Not proposed as a lane change. An additive upstream seam
  is drafted instead** (hand-back: `UPSTREAM-DRAFT.md`, two API shapes mirroring the public
  `extensionFactories`/`extensionsOverride` options; owner decides on submission at R4).
- **B. `scanPeerOwners`:** our code, ≤ 22 % of the headerless baseline and **0 for orchestrated callers** —
  fails the rule on both baselines, and it is C5's fail-closed lineage mechanism (a semantics-sensitive surface).
- **C. `subagent` transpile:** measured as a non-cost (warm ≈ cold); additionally excluded by the B1.2
  owner decision (option C). Non-candidate.

**Verdict: no qualifying change — the brief's honest "no safe saving found" branch**, accepted by the parent
(`01-answer.md`). The lane makes no product change; the numbers above are the baseline any future change must
beat, measured with this same instrument.

## 5. Follow-up candidate for R4 (analysis only, no code; parent-requested)

**Reuse the pre-pass `resolve()` result across creates under a fingerprint.** The B1.2b pre-pass in
`buildFactoryBackedLoader` runs a full `packageManager.resolve()` (~half of the 130.6 ms above, ≈ **65 ms/create**)
but consumes only `enabledOrder` — the enabled extension paths in resolution order — which feeds
`additionalExtensionPaths` and the parity label/order restore. That list is plain path data (safely shareable as
immutable strings) and depends only on (cwd, agent dir, global settings, project settings chain, extensions tree,
project-trust state).

- **Shape:** a bounded per-(cwd, agentDir) map of `enabledOrder` lists, revalidated against a fingerprint that
  bundles the extensions-tree fingerprint the factory cache already computes per seed (~4.5 ms) with the stat of
  the settings files in the global+project chain. Miss or mismatch → recompute (today's path).
- **Estimated saving:** ≈ 60 ms/create net of fingerprint cost ≈ **12–15 %** of the orchestrated baseline —
  **does not meet the 30 % rule alone** (correctly out of scope for this lane), but it composes with an accepted
  upstream skills seam later.
- **Risks:** a stale `enabledOrder` mislabels or mis-orders extension entries (visible, but a correctness risk
  class the B1.2 reviews scrutinised); the fingerprint must cover the whole settings chain including
  trust-affecting state, or a project enable/disable change could apply one create late; the cwd-keyed map needs a
  bound (worktree churn creates many cwds); the per-create `SettingsManager` must stay unshared (it carries
  project-trust state) — only the derived list is cached.

## 6. Side observations (routed, not fixed here)

1. **`DELETE /api/v1/sessions/:id` costs a fixed ~1005 ms wall per session** (median 1004–1007 ms in every phase,
   every n) with ~0 main-thread work — timer-shaped. Every Internal API child teardown pays it. The parent routes
   this to R4.
2. **The B2 admission lag gate latched under CPU-profiler overhead:** the first profiled attempt (200 µs sampling)
   tripped `event_loop_lag` and drew 503 `ADMISSION_CAPACITY_EXHAUSTED` refusals after ~23 creates; that run is
   archived and excluded from every number above, and the accepted profiled pass ran with the gate raised
   (`INTERNAL_API_ADMISSION_LAG_P99_MS=5000`) while the clean pass used the default 300 ms. Independently confirms
   B1.2 §17's warning: per-create main-thread spikes of this class can latch the 300 ms gate under load.
3. **`agent-os-inject` spawns a client process per session create** (~9–10 ms/create) — upstream extension-store
   observation for its owner.

## 7. Deviations and environment findings

- `systemd-run -p Nice=` is rejected on this host ("Unknown assignment") — the brief's documented fallback
  (`nice -n 10` inside the unit; `-p CPUWeight=100` on the scope) was used.
- `systemd-run --scope` is synchronous and blocked the first launcher; service mode is used instead.
- Service mode does **not** inherit the caller's environment (an earlier `--scope` boot had leaked the dispatch
  shell's `NODE_ENV=production`/`PI_MAX_SESSIONS=20`), so the unit pins its env. Pinning `NODE_ENV=production`
  first made the server demand `JWT_SECRET`/`AUTH_PASSWORD` (the config production gate); the disposable server is
  designed dev-mode, so both passes run `NODE_ENV=development` with one shared admission profile.

## 8. Blind spots (what this evidence does NOT see)

1. **Sequential single-creates on an idle loop.** T1 measured creates under stepped concurrent load (its ~480 ms
   `resource_loader` average spans creates interleaved with streaming turns on a busier host). The two instruments
   are complementary, not contradictory.
2. **Production worktree cwds:** the cold cases used fresh empty directories. A real git-worktree cwd adds
   project-settings reads, `.agents/skills` ancestor walks to the git root and project-skill scans. Production
   cold creates are therefore somewhat worse than measured; the warm number is unaffected.
3. **Skills-corpus sensitivity:** 201 skills measured; the skills share scales roughly linearly with corpus size
   (it is already the top item).
4. **Other runtimes' create paths** (claude/opencode/antigravity/commandcode) are out of scope — runtime `pi` only.
5. **First-create warm-up** is one boot per pass (n=3); its composition (module/jiti warm-up) is named, not
   itemised.
6. **Headerless-caller applicability:** the `scanPeerOwners` cost applies only to creates without
   `X-Parent-Session`/`parentSessionId` (raw curl-style callers). Orchestrated callers do not pay it.
