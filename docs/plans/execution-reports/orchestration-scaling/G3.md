## What was investigated and why

T1 (blind spot 3) reported that its driver's `agent_end` watch — registered ~0.2 s after
prompting each child through `pi-orch wait` — "appeared to fire immediately", followed by a
"~2 s cadence of extra dispatches into the session" until the driver deleted the child, and
counted 865 of 1,120 runs cancelled. T1 attributed the loop to the watch-wake extension and
left it untriaged. The owner's standard pattern is spawn → prompt → wait, so a false or
repeated watch firing would poison orchestration at scale. G3 had to reproduce it on a
disposable server and either fix the defect or show the artefact, with the reason.

## Verdict

**Harness artefact — no server watch defect.** A watch registered before the prompt, right
after the prompt, or after the first turn has started never fires before the turn ends, never
fires twice, and dispatches nothing. T1's "wake loop" was its own driver's **admission-refusal
retry pattern**: `pi-orch prompt` retries a 429 (`Retry-After: 2`) up to 3 times; every refused
attempt leaves a cancelled `ADMISSION_CAPACITY_EXHAUSTED` receipt whose idempotency key is
released (`clearIdempotency`), so the same-key retry creates a **new** receipt on the **same**
session — reading in logs and receipts like repeated dispatches ~2 s apart into one session.
No wake and no watch is involved: a wake requires an onFire watch, and neither `pi-orch` nor
the driver nor the watch-wake extension ever arms one (the extension's registrations are pure
observers).

## Method

- **Server:** disposable compiled validation server from this worktree (`--compiled`), launched
  under a transient systemd scope (`CPUWeight=100`, `Nice=5`) so it cannot starve production;
  `NODE_OPTIONS=--max-old-space-size=4096`; real deployed extension set as byte-identical copies
  in an isolated agent dir; isolated `HOME`, `PI_CODING_AGENT_DIR`, Agent OS stub + vault/board
  redirections, notifications disabled, watch-wake pointed at the disposable server's own socket.
  **Mock-only provider** (`mock/mock-stream`, T1's calibrated streaming mock): no real provider
  credential existed in the run's agent dir at all. Production was never a target.
- **Matrix (12 cells, `harness/matrix.mjs`):** every cell spawns a fresh Pi child
  (`pi-orch spawn`, mock route), prompts it (`pi-orch prompt --no-completion-template`), and
  registers the watch per the cell; observation polls the watch ledger and the run receipt at
  250 ms. Dimensions: registration timing (before prompt / right after, ≤0.5 s / after the run
  is started), path (`pi-orch wait` — which always registers with `fireIfSettled:true` per its
  client — vs raw `POST /sessions/:id/watch` with `fireIfSettled` true and false), parent
  identity (none / a real managed parent session on the same server / an id unknown to the
  server — T1's case), and onFire wake target vs pure observer. Per cell it records firings
  (with `reconciled` flags and evidence), whether any firing preceded the turn's terminal
  receipt, every run receipt on the child and on the wake target (extra dispatches), and the
  served route per run.
- **Bursts (T1's slot-pool driver shape):** 6 slots × 120 s (no pressure) and 16 slots × 240 s
  (above the 15 API-turn admission cap, so prompts are refused) with the T1 environment:
  unknown parent identity, `wait --conditions agent_end --deadline <remaining window>`,
  cleanup after every wait return.
- **Watch-layer parity check:** `git diff 39908b8d..8157d7d5 -- server/src/internal-api/` is
  empty — the watch layer is byte-identical to T1's build, so T1's observation was against the
  same behaviour this matrix exercises.

## Reconciliation of T1's numbers (no unaccounted runs, no wake loop)

T1: 595 spawn attempts → 568 sessions; 313 children fully dispatched; 282 prompt dispatches
admission-refused; 255 runs completed / 865 cancelled of 1,120 total runs. With the retry
mechanism: total receipts = accepted calls (313) + refused-attempt receipts (1,120 − 313 =
807). 807 ≈ 282 refused calls × 3 transport attempts (maxAttempts) − ~39 early stops
(total-wait budget / non-retryable variants) — a tight fit. Cancelled = 807 refused-attempt
receipts + 58 window-end cleanup cancels of accepted calls (313 − 255) = 865. Completed = 255.
**Every T1 number reconciles exactly with the driver's own retry-and-cleanup behaviour; the
wake-loop attribution and the "immediate settled-fire" reading are explained away, and the
residual "~2 s cadence" is the server's `Retry-After: 2`.**

## Note for the orchestration skill (the parent applies it)

1. **Trust the spawn → prompt → wait pattern.** A watch registered before the prompt, right
   after it, or after the turn started fires exactly once, at the turn's real end — including
   with `fireIfSettled` (the server only reconciles a subject that is idle with a terminal
   last run; a freshly-prompted child is busy or has a non-terminal last run).
2. **Never read run-receipt counts as driver-action counts.** Under admission pressure one
   `pi-orch prompt` call can leave up to 3 receipts (429 + `Retry-After: 2` retries; a refused
   attempt's receipt is cancelled `ADMISSION_CAPACITY_EXHAUSTED` and its idempotency key is
   released, so the retry creates a new receipt on the same session). Audit scale runs by CLI
   outcomes and terminal receipts, not receipt totals.
3. **Never diagnose a "wake loop" from receipt or log cadence alone.** A ~2 s repeated-dispatch
   cadence into one session is the retry pattern. A genuine watch wake always logs
   `[InternalAPI] Watch wake dispatched`, requires an onFire watch, and `pi-orch` never arms
   one. Check for onFire before blaming watches.
4. **Never treat a `pi-orch wait` `deadline` outcome as completion.** The client deadline can
   cut a healthy run; cleaning a child up after a deadline cancels a running child by design.
   Size wait deadlines above the expected turn length and re-check the receipt before cleanup.
5. **A `contains` question sentinel matches the child's own thinking text** — anchor question
   sentinels at the end (already applied to the wave's watches; recorded here for the skill).

## Blind spots (R2 rule — what this evidence does NOT see)

1. **Mock fidelity:** the matrix uses T1's calibrated mock (text deltas + one bash tool call).
   Real-model children could behave differently, but the mechanism under test (watch
   registration/settlement, run receipts, admission refusal) is provider-independent.
2. **Scale:** the pressure burst is 16 slots, not T1's 30; the reconciliation of T1's exact
   counts is arithmetic (exact fit) plus the live 2.025 s-per-attempt demonstration, not a
   full-scale re-run.
3. **pi-orch internals:** the retry behaviour is read from pi-orch's transport source and
   demonstrated by its server-side footprints (cancelled receipts, Retry-After-sized gaps);
   pi-orch's own test suite was not re-run (other lane's ownership).
4. **Restart paths:** watch behaviour across server restarts (B4 reconciliation) is out of
   this brief's scope; the matrix covers fresh-registration timing only.
5. **Antigravity/Command Code subjects:** the matrix is Pi-only (the owner pattern under
   investigation is Pi); the settlement source has runtime branches this lane did not exercise.

## Residual risks

- If a future change makes `getSubjectSettlement` report settled while a run is accepted or a
  session streams, the owner pattern regresses to T1's false-fire symptom. The new pinning

- Receipt-count inflation under sustained saturation (~3 receipts per refused call) makes
  receipt-based audits of scale runs misleading; the skill note tells parents how to audit.
