## What shipped

Every Internal-API-created child is now traceable to its parent even when the caller sends no `X-Parent-Session`:

1. **New resolver module** `server/src/internal-api/parent-resolver.ts` — peer-credential caller resolution. Node exposes no SO_PEERCRED on this runtime (verified: `net.Socket#getPeerCredentials` is `undefined`), so the resolver reconstructs peer credentials read-only: accepted-socket inode (`/proc/self/fd/<fd>`) → client pid(s) via `ss -xp state established` (unix_diag; right-anchored parser handles ss with and without the State column) → bounded (≤32-hop) `/proc` ancestry walk reading `PI_WEB_UI_SESSION_ID` (contract 1.47.0; Claude, Antigravity, Command Code subprocesses) then `PI_SESSION_ID` (pi tool subprocesses; pi's bash tool sets it — verified in the SDK's `core/tools/bash.js`). The value must name a registry session; ambiguity (candidate pids disagreeing) or a bogus identity links **nothing**. The server's own environment is never consulted (walk terminates at `selfPid`), so a stale inherited variable on the server can never link.
2. **Route wiring** (`server/src/internal-api/routes/sessions.ts`): source order on `POST /sessions` is header → body → in-flight bash correlation → peer. An explicit value that fails to resolve stays unlinked (the peer walk never overrides what the caller explicitly named). `POST /sessions/adopt-native` gains the same fallback when no parent is named. `POST /sessions/:id/adopt` and session-control `adopt` deliberately keep the explicit parent **required** — forgetting the header there is a hard 400, not a silent unlink (recorded decision).
3. **Wire additions** (all additive): `parentSource: "header" | "body" | "bash" | "peer"` on the create response, adopt-native response (when linked), `GET /sessions` items, and `GET /sessions/:id` + `/info`; registry field `parentSource` (`patchSessionMeta` extended); `GET /sessions?parent=<id-or-path>` returns exactly that parent's children, `404 SESSION_NOT_FOUND` for an unresolvable parent value.
4. **Validation surface**: `parent-lineage` live-validation scenario (deterministic, zero model turns), `listSessions(parent?)` / `getSocketPath()` / `getToken()` on the validation client, header passthrough on `createSession`, `socketPath` in the validation context.

## Design decisions

1. **Peer credentials via `ss -xp` (unix_diag), not SO_PEERCRED** — Node has no SO_PEERCRED binding (verified on this Node v24 runtime), and the parent's note allowed exactly this evaluation. Cost: one `ss` invocation per unattributed create (creates are rare; no cache, so no stale-snapshot misses). Falls safe to no-linkage if `ss` is missing.
2. **Identity variables trusted at header parity** — `PI_WEB_UI_SESSION_ID`/`PI_SESSION_ID` are server/harness-set values; a hostile client could forge them exactly as it could lie via `X-Parent-Session`, the trust level contract 1.34.0 already accepts (display-only metadata, local same-user socket). Two safeguards exceed the header: registry validation of the resolved value, and ambiguity → no linkage.
3. **Adopt-session keeps the explicit parent mandatory** — changing a required field into an inferred one is a semantics change beyond lineage-fill; parents forgetting the header there get a clear 400, not a silent unlink. Applied only where unlinking was silent: create + adopt-native.
4. **`?parent=` 404s on an unresolvable parent** — a typo must not masquerade as "no children" (that is exactly the class of lie C5 exists to end).
5. **No ss cache** — a cached snapshot could miss a just-accepted connection (missed linkage); at create frequencies the subprocess cost is noise.

## Residual risks / cannot-see items

- `ss -xp` output format is stable on this host's iproute2 but the parser is right-anchored defensive (listens/invalid lines ignored; unparseable → no linkage). A future iproute2 column change degrades to no peer linkage, never a wrong link — but it would be silent; the `parentSource=peer` counter dropping to zero is the observable.
- Processes that scrub their own environment (e.g. `env -i curl …`) defeat ancestry attribution → unlinked (fail safe).
- Candidate pids > 8 per connection (heavy fd inheritance) are truncated; all truncated walks agreeing would still link, disagreeing walks never link.
- Root-only readability of `/proc/<pid>/environ` is assumed (production and validation both run as root); a non-root deployment would silently lose peer linkage (header/body/bash still work).
- The 100%-coverage claim is only meaningful after C1's live test; C5's own runs covered 5/5 managed-caller children + 1/1 realistic child (numbers above are item-level counts from the quoted outputs, not summed categories).

### 1. Ambiguity is fail-closed — DONE

- Owner attribution no longer reads ss's `users:` column at all. ### 4. execFile maxBuffer — DONE

- `runSs(command, args, maxBuffer)` classifies `ok` / `overflow` (ENOBUFS / `ERR_CHILD_PROCESS_STDIO_MAXBUFFER` / message match) / `unavailable`. Owner attribution comes from the `/proc` scan either way, so output stays small in the common path.
- Overflow → **no linkage** plus a rate-limited warning (one per 60 s, injectable clock; tested: two overflows in-window → 1 warning, after the window → 2). Overflow tested via a real `execFile` (`sh -c 'yes | head -c 200000'`, maxBuffer 1024 → `overflow`; missing binary → `unavailable`).

### Correction-round blind-spot note

The `/proc` owners scan replaces ss's `users:` attribution: processes that vanished between snapshot and scan (empty owner set) give no linkage (fail safe), and the scan reads only /proc entries the process can read (root in production and validation). The narrow ss filter depends on iproute2 honouring `src <path>`; if it silently stops matching, the resolver transparently falls back to the full table — the observable cost is one extra subprocess, never a wrong link.
