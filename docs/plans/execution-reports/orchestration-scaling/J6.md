## What changed

1. **The launcher owns the environment contract** (`scripts/validation-server.ts`,
   `server/src/live-validation/validation-server-env.ts`). Every inherited
   `PI_TOOLS_*` key is stripped from the disposable server's environment before
   the env file is loaded, and the strip is logged (`dropped inherited
   placement env: …`). The strip is unconditional by design: the env-file loader
   only fills *missing* keys, so a surviving ambient value would silently
   override the caller's explicit file value — caught live in the Phase B proof
   (arm2 of run `20261002T133739Z`: the child received production's anchor name
   instead of the run's own unit) and fixed in `5ed4c8e6`. The explicit channel
   for a placement proof is the existing `--env-file` + `--env-key`; the file is
   the only source of a placement value. `buildValidationIsolationEnv` pins
   `PI_TOOLS_RUNTIME_DIR` inside the validation directory, so wrapper and
   degrade artifacts never land in production's `~/.pi-web-ui/placement` even
   for an explicitly placement-enabled proof.
2. **Defence-in-depth in the server** (`server/src/placement/validation-gate.ts`,
   sweep call sites in `server/src/index.ts`, `server/src/placement/cleanup.ts`),
   per 01-design.md §3.2 as hardened by 01-answer.md: in validation mode
   placement is refused against the production anchor and tools slice by NAME
   and by ABSOLUTE PATH (decided pre-resolution, before any
   `cgroup.subtree_control` write), against any RESOLVED root at or under
   `pi-web-ui-tools.slice` (whatever the anchor is called), and against the
   server's own cgroup (equal or ancestor). A refusal skips resolve and sweep at
   startup, zeroes the applied config so the shutdown sweep no-ops, logs
   `[Placement] DISABLED — validation mode refuses …` and records
   `validation-placement-refused` in the degrade log. `sweepAllGroups` now
   returns zero for a config whose placement is not enabled (the sweep is a
   placement mechanism and can never again run on an unapplied config).
   Production behaviour is unchanged outside validation mode.
3. **Heap-soak belt** (`scripts/heap-soak/launcher.ts`): the soak server unit
   gets `UnsetEnvironment=PI_TOOLS_PLACEMENT PI_TOOLS_SLICE PI_TOOLS_CGROUP_ROOT
   PI_TOOLS_RUNTIME_DIR`, so a future manager-environment leak
   (`systemctl set-environment`) cannot reach it. Probe-proven on this host's
   systemd 255 (control unit saw a `--setenv` value; the belt unit saw nothing,
   `printenv` exit 1); not exercised end-to-end with a soak run.

Production server code changed (item 2): ships with this wave's restart, owner
grant on record. The launcher fix (item 1) protects every disposable server as
soon as lanes run the launcher from their worktree; no restart needed for it.

## Correction round 02 (Luna review round 1: REJECT; 02-correction.md)

All three findings addressed at `fc4ee4aa` + `04031352` + `81513e6a`:

1. **[blocker] Canonicalise before any write; sweep only a validated root.**
   `candidateToolsRootPath` extracts the candidate path read-only (slice NAME
   via `systemctl show`, absolute verbatim); `resolveToolsRoot` canonicalises it
   (`fs.realpathSync`, new `realpath` dep) BEFORE the `cgroup.subtree_control`
   write, refuses a root that cannot be canonicalised and re-checks cgroup-root
   containment on the canonical path (a symlink can never hide its target). In
   validation mode the whole gate runs on the CANONICAL candidate before
   resolution (`validationPlacementRefusalForConfig`) — a refusal means no write
   of any kind. `startupSweepConfig` gates both sweep call sites in `index.ts`
   to an ACTIVE applied config: a failed resolution leaves nothing sweepable (a
   raw absolute `toolsRoot` previously survived a failed resolution and would
   still have been swept). Production's normal path (slice name → resolved,
   verified root) still sweeps at startup — pinned by the fake-io test
   "a production-shaped config (slice name) still resolves and the startup sweep
   still reaps a planted group".
2. **[major] Own-cgroup comparison in one coordinate system.**
   `readSelfCgroup()` is cgroup-relative, resolved roots are filesystem paths;
   the unconverted comparison never matched (the refusal was dead code). Both
   sides are converted with the configured cgroup root before the
   equality/ancestor check. RED: the production-shaped relative/absolute pair
   was allowed pre-fix.
3. **[minor] Assertion count.** Corrected throughout this file: run
   `20261002T134124Z` had **29 `ASSERT OK` / 0 `ASSERT FAIL`** (`grep -c` on
   `progress.log`; the earlier "30/30" and the per-arm sum of 31 were
   unsourced); the final run `20261002T150809Z` has **37 / 0**, counted the
   same way.

## Blind spots (what this evidence does NOT cover)

- **Production restart behaviour is unproven here** (by design — production is
  never touched): the validation gate is dead code in production mode; the
  changed `sweepAllGroups` enabled-invariant and `index.ts` wiring DO run in
  production and ship with the wave restart. The unit suite covers the
  invariant; a post-restart production smoke check (placement still verified,
  startup sweep still reaping) is the parent's rollout step.
- **Heap-soak belt is not exercised end-to-end**: the `UnsetEnvironment`
  property is probe-proven at the systemd level and added to the launcher's
  unit spec, but no soak run booted with it.
- **The explicit channel still trusts the caller**: an explicitly designated
  FOREIGN root (not the production slice, not the server's own cgroup, not
  created by the run) would still be swept at startup — that is placement's
  amendment-B semantics, reachable only through a conscious `--env-file` act.
  The parent accepted this scope at the design gate.
- **Client/renderer**: no client code changed; no browser validation needed.
- **Other launchers that spawn servers**: `scripts/live-validate.ts` and
  `scripts/long-horizon-validate.ts` are clients (verified: no server spawn, no
  env construction) — unchanged. Any FUTURE launcher that spawns a disposable
  server must go through `buildValidationIsolationEnv` + the strip; nothing
  enforces that mechanically (a future guard could lint for it).
- **`--scope`-launched servers outside this launcher** (raw `tsx
  server/src/index.ts` runs): out of scope — the brief's launchers are the
  supported paths; a raw server boot is not a disposable-server launch.

## Residual risks

- The gate's production-name constants (`pi-web-ui-tools.slice`,
  `pi-web-ui-tools-anchor.service`) are deployment names; if production's tools
  slice is ever renamed, the constants must follow (single constants, unit
  tests pin them; the resolved-root check covers any path UNDER the slice, so
  only a slice RENAME weakens the tripwire, and the own-cgroup check still
  holds).
- The 11 full-suite load flakes pre-date this lane (they fail under parallel
  load and pass alone; recorded both ways above) — worth a dedicated lane, not
  this one.
