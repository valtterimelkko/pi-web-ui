## 4. Amendment-A sizing (per-child defaults)

Disposable `d0-sizing` unit (Delegate=yes, MemoryMax=24G, CPUQuota=400%, Nice=10), group `sized`, no limits (measurement run): full server unit suite **6051 passed \| 3 skipped (exit 0)**, `memory.peak` **1 855 492 096 B (1.73 GiB)** (includes page cache; anon peak ≈ 430 MB), `pids.peak` **138**; `npm run build` peaked below the suite. Decision rule (01-answer.md A): max = max(8 GiB, 1.5×1.73 GiB) = **8 GiB**; high = max(6 GiB, 1.2×) = **6 GiB**; pids = max(2048, 2×138) = **2048** — the answer's floors hold. Ordinary heavy work never meets a limit (peak 1.73 GiB ≪ 6 GiB high; 12 × anon ≈ 5 GiB ≪ 14 GiB slice high).

## 5. Disposable adversarial proof (contained; correction 03 + Memory-containment rules)

**Containment:** one delegated transient **service** (`d0-proof-run.service`, `MemoryMax=12G`, `MemorySwapMax=1G`, `Delegate=yes`, `OOMPolicy=continue`, `OOMScoreAdjust=-500`) holds the server, the mock provider and every proof command. The tools subtree is **nested inside it** (`<unit>/tools`, memory.max 10G/high 8G, `+memory +pids` enabled on the subtree — the no-internal-process bootstrap moves the server into `<unit>/control` first). Pre-arm assertions abort unless: ≥12G host-available, the scope's `memory.max` is numeric ≤ 12G, the tools subtree is nested under the unit path, and it exposes the memory controller. Arms run one at a time. The (b) allocation **self-caps at 10 GB**; the proof uses a 2 GiB per-child `PI_TOOLS_PER_CHILD_MEM_MAX` override so the kernel limit acts first. Harness: `/root/d0-runs/proof/` (driver `proof.mjs` via `pi-orch` spawn/prompt/wait/result/cleanup; raw transcripts preserved per child).

## 6. Proof-caught defects (fixed with RED tests)

1. **Limit-write bug**: wrappers gated limit writes on the leaf's `cgroup.procs` being absent — never true on a real cgroup — so per-child groups ran unbounded inside the slice. Discriminator is now the `memory.max` **value**; regression test drives the real script against a kernel-shaped fake leaf.
2. **Slice-name/path confusion (the 16:56 host OOM)**: `PI_TOOLS_SLICE` was treated as a path, so an unresolved name became a cgroup-root-level tree the wrapper created without limits. Now: names resolve via `systemctl show` (unknown → loud start-up failure, placement disabled), absolute paths must sit under the cgroup root, relative garbage rejected; the tools root is **never created** by server or wrapper and is verified (exists, memory controller, numeric bound within 4 ancestor levels) at start-up and per command.
3. **Non-all-or-nothing limits**: limits are now written then read back; mismatch removes the group and falls open with `limit-readback-failed`.
4. The containment worked under the failure: in the bootstrap-defect run the unplaced 10 GB alloc was stopped by its own self-cap inside the 12G unit — no host impact.

## 7. Blind spots (for §1.1 adjudication)

- **bg_run detached tasks and subagent children are placed via the pi-enhancement lane** — deployed to `~/.pi/agent/extensions` only at rollout; until then production's `bg_run`/subagent stay unplaced (bash tool of server-managed sessions is the heavy path and is placed).
- **grep/find tool subprocesses** (`rg`, `fd` inside the SDK) stay in the control plane (short, bounded); not worth the risk now — recorded, not hidden.
- **Web UI terminal** (operator pty) intentionally unplaced (answer 04: parent puts it to the owner at R4; one-line switch).
- **(a)'s placed-vs-unplaced contrast on an idle host** is narrower than the production incident (103 vs 422 ms, both arms' steady state ~1–4 ms): the 06:55-class failure needed co-tenant load. The structural evidence is (b)'s isolation and the cgroup topology.
- **(c)'s lag series is thin** (1 p99 reading) — the run finished fast; (a)'s 138-sample series is the denser lag evidence.
- **Per-child CPU** is weight-governed only (no `cpu.max` per child), by design (throttle-not-kill); on this systemd the delegated slice exposes `memory pids` to its subtree, which is exactly what the limits need.
- **Runtime subprocesses** (claude/opencode/agy/cmdc) are wired and unit-tested but the live proof exercised only the command-code class via fixture-free placement of bash/child paths; their spawn-site tests assert argv/env, not live provider runs (no credentials for those runtimes in the proof).
- **`vm.oom_kill_allocating_task`** was 1 during the incident and is 0 now (parent change) — the design does not depend on it either way.

## 8. Residual risks

- Production rollout touches systemd unit state (slice + drop-ins) — scripted in ROLLOUT, owner-gated, reversible per item.
- The OOMScoreAdjust drop-in lowers the whole unit's score; mitigated by the wrapper reset (proven) and the install-order constraint.
- `oom_score_adj` reset failure degrades + continues (a placed command could inherit -500 if the write failed — alarm fires via the degrade counter).
- Startup sweep kills all tools groups at server start: a command orphaned by a hard crash is killed at next start (documented behaviour change; amendment B).
