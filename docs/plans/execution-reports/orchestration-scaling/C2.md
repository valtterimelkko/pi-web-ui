## What was fixed (four accepted-then-lost / never-known shapes)

1. **Compaction is busy.** During Pi auto-compaction the manager's own status
   is idle (agent_end settled it) while the SDK refuses every input, so a
   prompt was accepted `202` and the detached run failed `RUNTIME_ERROR`
   ("Cannot submit a prompt while compaction is in progress") — the interim
   wave's observation, reproduced. Fix: `SessionStatusInfo` now exposes the
   public SDK `isCompacting`/`isStreaming` truth (read-only accessors in
   `server/src/pi/multi-session-manager.ts`, `readSdkActivityTruth`); Pi
   compaction makes `isSessionBusy` true, `evidenceStatus` report `running`
   (so `GET /sessions/:id` `busy:true`, the list, and watch settlement agree),
   and an explicit pre-dispatch refusal returns `409 SESSION_BUSY` with a
   compaction hint and `Retry-After`, for every mode, on both the prompt and
   the watch-wake dispatch path (`piBusyRefusal`, shared helper in
   `routes/sessions.ts`). B4.1's `listBusySessions` semantics are untouched
   (negative exclusion respected; the new accessor is additive).
2. **follow_up requires a live turn.** A Pi follow_up is a queue acceptance
   whose queue drains only when the live turn ends. Queuing behind a busy
   state with no live runtime turn (pre-start limbo, stalled turn) produced
   accepted-then-`TURN_STALLED` dispatches. Such dispatches are now refused
   `409 SESSION_BUSY` with a hint; idle promotion is unchanged, and queueing
   behind a genuinely streaming turn still works.
3. **Start detection (`NEVER_STARTED`).** A dispatched run (receipt status
   `started`) with no eligible activity and no output evidence ever observed
   is terminalised `failed NEVER_STARTED` inside a configurable start window
   (`INTERNAL_API_RUN_START_WINDOW_MS`, default 120000, `0` disables → legacy
   15-minute `TURN_STALLED` path pinned). The decision fires the operator
   notification (never-started wording, no quarantine claim;
   `stall-notification.ts`) and the parent's watch:
   `WatchManager.notifyRunNeverStarted` ingests a synthetic completion through
   the ordinary event path flagged `runNeverStarted: true` (the in-flight
   counterpart of `interruptedByRestart`; dataMatch-able the same way), and
   `condition-evaluator.ts` words the firing evidence. Queue-pending receipts
   are exempt — and are no longer terminalised `TURN_STALLED` at the idle
   window (a deliberate change; queue-pending is legitimate, and the
   2026-09-15 lost-wake shape is now refused at accept by fix 2).
4. **Post-terminal response fence.** A synchronous dispatch whose receipt was
   terminalised by an external decision (abort/delete/run-cancel/watchdog)
   while the runtime adapter never settled its promise used to hang without an
   HTTP response — the R2 input class (B3b residual 6). After the receipt is
   terminal, the dispatch waits at most `postTerminalSettleMs`
   (`INTERNAL_API_POST_TERMINAL_SETTLE_MS`, default 10000; route-level
   override for tests), then fences the execution (observers detached, Pi turn
   boundary resolved) and completes from the receipt's outcome with a new
   error code `RUN_TRANSPORT_LOST` + the `runId`. The receipt's external truth
   is preserved.

## Design decisions

- Refusal over queueing for compaction (the plan allowed either): refusal is
  honest, immediate, and needs no new queue lifecycle; the compaction window
  is short and `Retry-After` covers the retry.
- `NEVER_STARTED` as errorCode on a `failed` receipt (not a new status): the
  status enum is load-bearing (settlement, pruning, recovery classification);
  `TURN_STALLED` set the precedent of distinct errorCode on `failed`.
- Start watchdog scope = dispatched runs only (receipt `started`): queue
  acceptance is server-tracked delivery commitment, not a runtime start
  failure; the exemption also removes the old idle-watchdog lie about
  queue-pending receipts.
- Fence default 10s: generous against the normal terminal↔settle race
  (milliseconds), far under any client timeout, configurable.
- The never-started watch firing reuses the B4 boot-reconciliation pattern
  (synthetic completion through `handleEvent`, one wake, flagged data) rather
  than a new channel, so parent semantics are identical.

## Residual risks / blind spots (for §4 intent-check adjudication)

1. The start watchdog sees only Internal-API receipted runs. Browser (P0)
   turns and extension-driven turns hold no receipt and stay invisible to it
   (unchanged by C2; B4.1's drain view and B5's dispose paths are the
   mechanisms that see those — outside this lane's owned seam).
2. A queue-pending follow_up whose host turn NEVER ends keeps its receipt
   `queued` indefinitely; the turn itself is bounded by session disposal,
   drain and B5 dispose paths, not by this watchdog. The 2026-09-15 lost-wake
   shape (busy with no live turn) is refused at accept since C2.
3. The compaction check races the exact compaction-end boundary (milliseconds):
   a dispatch that passes the check and then hits the SDK refusal fails fast
   in the adapter as a failed receipt (RUNTIME_ERROR/SDK error) — loud, not
   lost, but not the tidy 409.
4. The fence bounds the synchronous answers/streaming dispatch chain; it does
   not create delivery guarantees for a receipt cancelled while the runtime
   continues unobserved (the runtime turn keeps its own session-level
   visibility).
5. Compaction-as-busy is Pi-only by definition (other runtimes' compaction is
   SDK-internal); the follow_up live-turn requirement is Pi-only (Antigravity
   keeps its native queue semantics).
6. Default start window 120 s: a runtime that legitimately takes >120 s from
   dispatch to ANY eligible activity event would be mis-filed NEVER_STARTED.
   `agent_start` fires at submission, so this requires a pathological
   provider queue; tunable via env, `0` disables.
7. Live trials consumed ~120 small zai/glm-5.3-flash model calls (within the
   authorised free lane).
