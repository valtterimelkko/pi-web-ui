## 1. What was fixed

**Retainer 1 — `PiService.sessions` (pi-web-ui).** `MultiSessionManager.disposeSession`
(Internal API DELETE via `disposeLoadedSession`, aggressive cleanup, stale-stream
reset), `unloadSession` (idle cleanup, eviction), `MultiSessionManager.dispose()`
and the failed-create cleanup removed only the event handler and never called
`piService.releaseSessionRefs`, so `PiService.sessions` kept every disposed
`AgentSession` alive forever. `SessionPool.createClientSession` /
`switchClientSession` / `removeClient` and `PiService.removeClient` had the same
gap. Every teardown path now funnels through one helper
(`MultiSessionManager.releasePiServiceRefs` → `PiService.releaseSessionRefs`,
which is identity-safe: a sibling owner of the same session id keeps the
`sessions` entry). `PiService.removeClient` and `SessionPool` use the canonical
`releaseSessionRefs` directly.

**Retainer 2 — the `subagent` extension's module-level `process.once("exit")`
(pi-enhancement).** Pi evaluates extension modules once per session, so each
loaded session added a process-level listener whose closure reached
`backgroundRuntime` / `backgroundStatusCtx` → the session context → the
`AgentSession`. The hook is now registered exactly once per process through a
`globalThis` `Symbol.for` registry and closes over nothing but `WeakRef`s to live
session managers. Last-resort abort-at-exit is preserved for every still-reachable
manager; a disposed session becomes collectable. `session_shutdown`
(`quit`/`reload`) also drops its weak registration after `shutdownAll`.

## 6. The host-side listener guard, and the gap it documents

The brief asked for a host-side test that loads an extension registering
`process.once("exit")` at module scope, runs create→dispose cycles, and asserts
`process.listenerCount("exit")` does not grow. The exact shape is **not achievable
at the host level**: the SDK owns extension loading and evaluates each extension
module per session (`dist/core/extensions/loader.js`, a fresh jiti with
`moduleCache: false`), and the host holds no handle on an extension's module-scope
closure. `server/tests/integration/pi-extension-exit-listener.test.ts` therefore
delivers the closest honest pair:

- the host's own lifecycle is flat: five create→dispose cycles leave
  `PiService` and `MultiSessionManager` maps empty and add **zero** exit
  listeners (RED before the fix); and
- the SDK-owned limit is pinned: three real loader evaluations of the fixture
  extension add exactly three listeners. If the SDK ever caches extension modules
  per process, that test fails and the host guarantee can be widened.

The actual retainer-2 fix is enforced where it belongs, in the extension store, by
`pi-enhancement/tests/subagent-exit-listener.test.mjs` (one listener, weak refs,
collectable context).

## 8. Not done, and why

- **The 24 h confirmation soak** and the deployment of the extension to
  `~/.pi/agent/extensions` are the parent's step (owner-gated). Only the isolated
  scratch overlay was live-tested.
- **Heap-snapshot counting in the disposable proof.** The brief's disposable proof
  asked for heap snapshots before/after a create/delete loop. This bundle uses a
  deterministic `WeakRef` + `--expose-gc` collectability assertion with the real
  `PiService`/`MultiSessionManager` instead of a snapshot count: it is the same
  claim at the object level, is cheap and repeatable in CI, and avoids the
  snapshot tooling A1 showed to be defective. The counted (snapshot/retainer-path)
  form is what the confirmation soak produces.
- **`A2` telemetry** (production before/after) is a separate lane.
- **`PiService.createSession`'s catch-path** already released its own references
  under an ownership guard; it was left as-is (routing it through the canonical
  helper would have deleted a concurrent newer session's handler for the same
  client id). The change to `PiService.removeClient` is sibling-preserving where
  the old code deleted the `sessions` entry unconditionally.
