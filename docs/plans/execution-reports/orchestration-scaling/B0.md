## 2. What changed

The A1 soak produced a false "complete" 19 h after its server OOM'd, and its
snapshot diff crashed on a 0-byte file. B0 makes the harness a trustworthy
instrument again. Six fixes, each with a pure, unit-tested core and I/O only
behind the existing seams:

1. **Server-death detection** (`server/src/live-validation/heap-soak/server-death.ts`,
   `scripts/heap-soak/liveness-io.ts`, `scripts/heap-soak/supervisor.ts`,
   `scripts/heap-soak/driver.ts`, `report.ts`, `run-state.ts`, `analyze.ts`).
   The supervisor checks the server unit's `LoadState`/`ActiveState`/`MainPID`
   and the Internal API socket every sampling cycle. Death is proved from the
   recorded unit/PID identity (`decideReattach`'s twin), **never** from a failed
   sample; a still-active unit with an unreachable socket is tolerated for up to
   `SOCKET_UNREACHABLE_STRIKES = 3` consecutive checks. A dedicated liveness
   loop (every 10 s) makes detection independent of the sampler, and the CDP
   inspector now fails in-flight requests the moment its connection drops, so
   a hung sample cannot delay detection. On death the load
   driver stops (`isStopped`), the run records a terminal `server_died` with
   the death time, last good sample, unit exit status and a bounded journal
   tail, `report.md` leads with a `SERVER DIED` section, and the final Telegram
   message says "server died at … after …" instead of "complete". Sample
   coverage is measured against the observed window, so a dead run no longer
   reports a fake 20 % coverage that hides the cause.
2. **Snapshot robustness** (`snapshot-selection.ts`, `snapshot-retainers.ts`,
   `snapshot-diff.ts`, `snapshot-diff-worker.ts`). The comparison now selects
   the latest *valid* (non-empty) snapshot, naming any skipped 0-byte file and
   falling back to the heap-threshold snapshots. The large-heap worker also
   ports A1's `analysis/retainers.mjs` and `analysis/cut2.mjs`: shortest
   retainer chains for the top growing object constructors and always
   `AgentSession`, plus a cut test showing reachable bytes/instances with and
   without the top named-property retainers.
3. **Sampler fields** (`types.ts`, `sampler.ts`). `residentSessionCount` and
   `registryEntryCount` were both the `GET /sessions` length.
   `residentSessionCount` is dropped: no existing server source exposes a live
   in-memory Pi session count (`/api/v1/capacity` has no such field;
   `/api/v1/diagnostics`'s session counts are registry-derived;
   `MultiSessionManager.getMemoryStats().sessionCount` is never routed).
   `registryEntryCount` stays. The ~1,700 sessions at t=0 are the deliberate
   registry seed (`registry-seed.ts`, `DEFAULT_SYNTHETIC_REGISTRY_COUNT =
   1700`, written to the per-run `validation/session-registry.json`), not a
   foreign-registry leak — see §5.3.
4. **Soak memory limit** (`resources.ts`, `launcher.ts`). The unit now runs
   `MemoryMax=12G`/`MemoryHigh=10G` (was `MemoryMax=6G`). A1's final sample
   shows RSS 5,789 MiB at the 4,044 MiB heap cap; admission pressure triggers
   when `(MemoryMax − RSS) − (activeTurns+1)×512 MiB < 512 MiB`, so at the
   soak's ≤7 active turns (`maxConcurrent` 6 + 1) the 12 GiB cap throttles only
   above ≈6.5 GiB RSS — the V8 heap cap binds first, which is the point of the
   soak. The 12 GiB cap is itself the host-safety cap (31 GiB host).
5. **Production-write audit attribution** (`prod-audit.ts`,
   `prod-audit-io.ts` callers). Needles are now the isolated **child-workspace**
   path (`<runDir>/children/…`, the child's cwd) and the run's child session
   ids — markers only a soak child emits. The bare run id **and** the bare
   run-dir path are **removed** as needles: the run id false-positived on the
   seven operator sessions / Agent OS captures that merely discussed A1, and
   the run-dir path was found live at B0 to false-positive on the harness's own
   orchestration bg-task log and the operator transcript (see §5.5).
6. **Extension overlays** (`extensions-overlay.ts`, `launcher.ts`, `start.ts`,
   `gate1.ts`, `cli.ts`, `run-state.ts`, `report.ts`). `start` and `micro`
   accept a repeatable `--extensions-overlay <dir>` (a single extension dir, or
   a directory of extension dirs). Overlays are copied over the isolated agent
   dir's production extensions, recorded in `run-state.json` and rendered in
   `report.md`, and never touch `~/.pi/agent/extensions`.
7. **Startup recovery and an honest report on a dead nonterminal run
   (correction 02)** (`server-death.ts`, `supervisor.ts`, `analyze.ts`,
   `run-state.ts`). A supervisor that restarted into an already-dead server
   (it died during the supervisor's systemd restart window) used to log, send a
   generic blocked notice and exit, leaving the run nonterminal; a later
   `report` then defaulted it to a full-schedule `complete`. Startup recovery
   now terminalises idempotently from saved state + unit identity
   (`recordServerDeath`), collects the unit exit status and a bounded journal
   tail, writes the death report, and sends the death notice exactly once
   (`deathNoticeSentAt`). The normal end persists `terminalState='complete'`.
   `resolveReportedRunOutcome` makes `report` render a nonterminal run whose
   server is gone as `server_died` — never `complete` — while a run that
   recorded `complete` stays complete after its transient unit is collected.
8. **Completed runs are never reclassified; at-least-once notices (correction
   03)** (`server-death.ts`, `supervisor.ts`, `run-state.ts`). Round 2 found
   that startup recovery would overwrite a persisted `terminalState: 'complete'`
   when the server unit was gone later (a normal stop, a collected unit, or a
   post-completion crash). `recordServerDeath` and
   `shouldTerminaliseOnStartupRecovery` now leave `complete` untouched, so a
   restart after completion only finalises the completed run (report + done
   notice) and never rewrites it as a death. Startup recovery exits 0 once the
   run is terminal, so systemd's `Restart=on-failure` cannot loop. The final
   Telegram notice is **at-least-once, normally once** (documented, not
   engineered): it is sent before its marker is persisted, so a crash in
   between re-sends it; `shouldSendFinalNotice` pins that semantics and no
   outbox machinery is used.

### 5.3 Sampler-column investigation (the 1,702 sessions at t=0)

The disposable server is seeded with `DEFAULT_SYNTHETIC_REGISTRY_COUNT = 1700`
synthetic registry entries (`registry-seed.ts`) before boot, so `GET /sessions`
returns ~1,700. That is deliberate production-fidelity (production's registry
is ~1,700 entries), the entries point only inside the run dir, and the seed is
written to the per-run `validation/session-registry.json`. The old
`residentSessionCount` column simply duplicated that registry count under a
second name, which is why A1 showed "resident" rising with the registry. There
is no foreign-registry or rehearsal-session leak: the entries are
`synthetic-####` ids owned by the run. Fix = drop the duplicated column (§2.3),
not an isolation change.

### 5.8 Completed-run restart regression (correction 03)

The round-2 defect is pinned by a pure regression test (no live control is
needed, and a full 20-minute micro completion would not add signal):

- `recordServerDeath` called on a run with `terminalState='complete'` leaves it
  `complete` and sets no `serverDeath`;
- `shouldTerminaliseOnStartupRecovery` returns false for `complete`, false for
  an already-recorded death, true for a nonterminal run and for a
  `server_died` state missing its evidence;
- `shouldSendFinalNotice` pins at-least-once: no marker → send; marker set →
  don't.

RED on the pre-correction code (`expected 'server_died' to be 'complete'`, plus
`is not a function` for the two new helpers) → GREEN 22 passed.

## 7. Not done and residual risks

- The A1 retainer analysis parses the 2 GiB snapshot in the worker; the
  combined-size guard still skips comparison entirely above 1.5 GB combined, so
  a run whose start+latest snapshots exceed that would get DevTools instructions
  rather than an in-process retainer summary.
- Coverage is now scoped to the observed window on a death; the
  definition-of-victory 95 %-of-24 h check is only meaningful for a run that
  actually reaches the window.
- The retainer cut test reports reachable bytes with cut nodes still counted
  (cut2.mjs semantics: a cut node is not expanded but its own self-size is
  counted), so the "bytes freed" is a lower bound relative to a full removal.
- The overlay worker copy runs before the server boots; an overlay that changes
  an extension's runtime behaviour is exercised by the run but not separately
  asserted here beyond the file/checksum checks.
- Compatibility: the CSV column removal changes the header for runs from this
  build on; `parseCsvWithHeader` reads older CSVs (with the extra column) by
  header name, so prior artefacts remain parseable.
- The final notice is at-least-once, not exactly-once: a crash between a
  successful send and the marker write re-sends it on restart. This is the
  accepted design (correction 03), not an outbox.
