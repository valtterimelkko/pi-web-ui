# I2 — Server: every follow-up drained in one agent loop reaches a terminal receipt

Step I2 of the R4 interim fixes (orchestration-scaling plan §R4; H2 *Root causes* item 3). Build: lane branch `orch/i2`, worktree `/root/.worktrees/orch-scaling/i2-pi-web-ui`, from master `ea9fe96b`.

## What changed

`server/src/internal-api/routes/sessions.ts` — the queued Pi follow-up correlation:

1. **Stack correlation.** Pi drains queued follow-ups inside ONE agent loop and closes the whole drain with a single `agent_end` (read-only SDK confirmation: `@earendil-works/pi-agent-core` `dist/agent-loop.js` — the loop's would-stop point pulls `getFollowUpMessages()` and `continue`s; one `agent_end` at loop exit; abort early-returns WITHOUT draining, so the queue survives an abort). Previously `queue.find(delivered)` let the first delivered follow-up own the whole loop's events: a sibling's `message_start` was routed to the elder and never matched, so the sibling's receipt stayed `queued` forever (queue-pending receipts are exempt from the start watchdog and the stall reaper), and the elder's `finalText` was the whole loop's last assistant text — the wrong answer. Now: an armed sibling's matching `message_start` delivers it (marked started) even while an elder is active; events route to the most recently delivered follow-up; the single non-synthetic `agent_end` observes + completes **every** delivered correlation. Each follow-up's receipt therefore observes exactly the assistant text between its own user message and the next follow-up's user message (or the loop's end): `finalText` is its own answer.
2. **No indefinite `queued`.** A new settle reconcile runs at the loop's end (and periodically while undelivered receipts remain): an undelivered receipt is terminalised `failed` / `NEVER_STARTED` when the runtime can no longer deliver its message — armed (queue entry removed from a `queue_update` shrink) but no matching user `message_start` ever came; unarmed but the SDK queue snapshot no longer holds the message; or the loaded agent itself is gone (idle unload/eviction: the queue died with it). An undelivered receipt whose message is still in the SDK queue stays `queued` **by design**: the SDK's abort path keeps the queue (verified in SDK source and pinned by test C), so a later loop can still deliver it; session delete ends it `cancelled`, a server restart `interrupted`/`SERVER_RESTART` (both pre-existing).
3. **Settle sweep.** Per-session `setInterval` (deps-injectable `followUpSettleSweepIntervalMs`, default 30 s, `unref`'d, cleared when the queue empties and in the existing per-session disposal handle) re-runs the reconcile for sessions that still hold undelivered follow-up receipts after a settle — this is what catches the idle-unload drop path, which emits no event.

Contract **1.58.1** (patch, inside the C6 window): receipt-status behaviour change only — no new route, field, error code, event or default. The client snapshot regenerates with exactly one line changed (`contractVersion`); the stability-window fingerprint is therefore unchanged (its guard test stays green).

## Not done and why

- **Production deploy**: outside a lane's authority; the parent owns the restart (plan victory clause "production deploy under the owner's restart authority").
- **No new error code** (`FOLLOW_UP_DROPPED` was considered): `NEVER_STARTED` already carries the exact consumer meaning ("nothing ran; re-dispatch") including watch-side synthetic-completion notification; a new code would force a snapshot regeneration, a stability-window exception row and an Agent OS mirror change for no consumer gain. Design decision recorded in `complete.md`.
- **The empty-final `/goal` arm receipt** (mechanism A) is I1/I3/H2 scope; it is terminal (`completed`, handler-return basis) and stays as-is here.
- **Idle-with-queued-message receipts are not auto-cancelled**: after an abort, a follow-up still in the SDK queue stays `queued` until delivered, deleted or restarted — terminalising it would be a lie (the message remains deliverable). Documented in `docs/INTERNAL-API.md`; callers cancel/delete if unwanted.

## Residual risks

- The settle reconcile trusts the SDK queue snapshot (`getFollowUpMessages()`) at reconcile time; a message removed and re-added between ticks could in principle be mis-dropped once — mitigated by reconciling only settled (non-streaming) sessions and by the armed/undelivered check requiring the queue_update shrink to have been observed first.
- The sweep polls (default 30 s), so an unload-triggered drop terminalises up to one interval late — accepted (better than never; session delete and restart already bound it).
- Live proof is one session per arm per build (n=1) — a semantics proof, not a distribution; the plan's reviewer re-run covers repeatability.
- The mock-provider 429-injection path (provider-error behaviour) was not exercised here — no provider error occurred in either arm (0 errored/aborted assistant messages), consistent with the root-cause report's finding that none of the G5 defects were provider failures.

## Correction 01 (focused race review, 2026-10-01)

Review: `reviews/i2-deepseek-review.md` (ACCEPT WITH FIXES); correction: `i2/01-correction.md`. Commit: **67cfdfb5**.

### Fix 1 — dead settle guard (wrong lookup key) [major]

`server/src/internal-api/routes/sessions.ts`, `reconcileDroppedPiFollowUps`: the busy/streaming gate called `multiSessionManager.getSessionStatus(sessionId)` with the Internal API session id, but the manager is keyed by session **path** (`pi/multi-session-manager.ts:1408`) — the lookup always missed, so a sweep tick landing inside a later loop's mid-drain window (queue_update processed, message_start not yet — the SDK emits the post-shrink queue_update before the public message_start, `agent-session.js:567-581`) terminalised a follow-up the SDK was delivering as `failed`/`NEVER_STARTED`. The reconcile now looks up by the correlation's `sessionPath` **and** defers on the SDK's own `isStreaming` truth (plus the status fields `sdkStreaming`/`compacting`), so a lagging manager status cannot open the window either.

### Fix 2 — sweep never armed without a non-synthetic agent_end [major]

The sweep was armed only from `reconcileDroppedPiFollowUps`, which only ran on a non-synthetic `agent_end`. A turn dying to the manager's synthetic `api_error_grace` `agent_end`, a follow-up queued on a session never prompted again, or a stale-stream dispose left the receipt `queued` forever — and `queuePiFollowUp`'s `waitForTerminal` never resolved, so the model read lease it took was never released and a later `setModel` would wait forever. The sweep is now armed at correlation creation (`queuePiFollowUp`, right after `queuedPiRuns.set`), and the drop reconcile runs for synthetic terminal events too (delivered runs still never complete on synthetic evidence — 15b semantics unchanged). Every terminal path releases the lease: completion and drop both go through `runReceipts.finish` → `waitForTerminal` resolves → `releaseModelLock()` (asserted by tests A/G/J `released>=1` and I).

### Fix 3 (found while verifying) — chain-lag drop window

The first full-suite run after fixes 1–2 failed test A once: under load, the per-session chain can lag a whole **finished** loop (each step awaits receipt-store IO), and a tick would read post-drain SDK truth (idle, not streaming, mirror spliced) before the chain correlated the delivery — the same false drop. The reconcile now defers while the chain still owes events (`queuedPiChainDepth`: pending-event counter incremented at hand-off, decremented in the step's `finally`); the count is cleaned up in `removeQueuedPiRun` and the per-session disposal handle. Reproduced deterministically by test J (a gated `markStarted` stalls the chain behind the first delivery while the second sibling's events queue up); mutation check: removing the depth guard fails A and J (`expected 'failed' to be 'queued'` / `'completed'`), with it all 10 pass.

### Minor — harness realism

The lane's harness entry now has `path: 'session-path-1'` distinct from its route id `session-1`, the `getSessionStatus`/`getAgentSession` mocks are keyed by path (as the manager is), `piService.acquireSessionModelLock` is spied for lease accounting, and the SDK simulator models the streaming truth (a draining loop is streaming until its agent_end) plus `drainBegins`/`deliverMessageStart`/`syntheticAgentEnd` primitives for the mid-drain and synthetic-end windows. A–F stay green.

### New residual risks (correction)

- The chain-depth deferral holds a drop decision only while events are pending; a session whose chain is fully drained but whose SDK is genuinely mid-drain (no queue_update observed yet) is covered by the streaming gates instead — the two windows are complementary, but a pathological SDK that reports idle while its loop runs would still be exposed (no such path known; the SDK's `isStreaming` is the loop's own state).

Accepted: nothing else terminalises that shape, and the alternative is an indefinite `queued`.
- Test J gates `markStarted` at the manager boundary; a future refactor that moves the delivered-flag set after the await would need the gate moved with it (the depth guard itself is production code and tested by A under load + J deterministically).
