## What shipped

- **Admission seam (shared verbatim with lane b2).** `AdmissionRefusalReason` gains `heap_pressure | event_loop_lag | draining`; `AdmissionController.setDraining/getDraining`; while draining, P2/P3 execution is refused with reason `draining`, P0/P1 control is still admitted. Nothing else in `admission-controller.ts` changed.
- **Drain state machine** (`server/src/internal-api/drain-controller.ts`): `idle → draining → settled | timed_out → (hold expires | cancel) → idle`. The settle wait needs **both** zero active execution turns (quarantined capacity debt excluded) **and** zero nonterminal run receipts (`accepted`/`queued`/`started`), bounded by a clamped timeout (default 600 s, max 3,600 s). Admission stays closed after the verdict until the restart, or reopens when a hold window (default 300 s) lapses with no restart. The verdict (with the cut-off run ids) is written to `internal-api-drain.json` beside the run-receipt directory.
- **HTTP surface** (`routes/drain.ts`, `server.ts`): `POST/GET/DELETE /api/v1/drain`, behind the existing bearer middleware, zod-validated strict body. A router gate refuses `POST /sessions`, `/sessions/batch`, `/sessions/batch/prompt`, `/sessions/:id/prompt`, `/sessions/:id/transfer` with **`503 SERVER_DRAINING`, `Retry-After: 30`**, before any receipt exists. Admission `draining` refusals inside the prompt pipeline (Pi goal control, Command Code, batch items) map to the same code; the pre-dispatch receipt ends `cancelled` / `SERVER_DRAINING`. Reads, control, abort, watches, approvals, adoption and `DELETE` are untouched.
- **Post-boot reconciliation.** The run-receipt store already recovered cut-off runs as `interrupted` / `SERVER_RESTART`. It now classifies them `interruptionReason: drain_timeout` (named in the previous process's drain record, consumed once at boot) or `server_restart`, and lists them. `WatchManager` then ingests one synthetic `agent_end` per watched session (plus `goal_end` when that condition is pending), flagged `data.interruptedByRestart: true` with `runId`, `runIds`, `errorCode`, `interruptionReason`, through the ordinary event path — once-semantics, `dataMatch`, `onFire` wakes and ledger persistence apply — and **before** downtime reconciliation, so nothing double-fires. Firing evidence: `event agent_end (interrupted by restart: run <id>, drain_timeout)`.
- **Deploy scripts.** `scripts/restart-production.sh` drains by default (POST drain → verdict → stop-audit record → notify → `systemctl restart <unit>`); `--drain-timeout N`, `--on-timeout restart|abort`; `--force` now **requires** `--reason` and records `drain=forced`; `--show-targets` prints the resolved targets and does nothing. 404 from an older server → legacy active-turn pre-flight; socket refusing / absent → proceed (dead daemon); drain timeout or other HTTP answer → refuse. `record-restart-requester.sh` adds a sanitised `drain=<verdict>` token to the `RESTART-REQUESTED` line. `with-production-lock.sh` routes a bare `[sudo] systemctl restart|try-restart|reload-or-restart pi-web-ui[.service]` through the drain path and is re-entrant for the same lock. New `npm run production:drain-restart`. `DEPLOYMENT.md` deploy flow uses it.
- **Contract 1.51.0** with changelog entry, `INTERNAL-API.md#drain-then-restart`, `SERVER_DRAINING` in the error catalogue.

## Design decisions

- **The drain never terminalises or aborts anything.** Graceful shutdown flushes receipts before disposal (`sessions.ts` `shutdown()`), so a cut-off run is still nonterminal when the process dies and the existing boot recovery marks it `interrupted`. Marking receipts terminal before the restart would lie if the restart then failed or was aborted, and firing watches before the restart would send `onFire` wakes into a draining server (refused). So there is one mechanism: the drain records *which* runs it expects to cut off, and the next boot classifies and fires.
- **Status name.** Kept the existing terminal `interrupted` + `SERVER_RESTART` (parents already handle it) and added `interruptionReason: drain_timeout` beside `server_restart`, so planned cut-offs are distinguishable from crashes without a new status value.
- **`goal_end` is also fired** (flagged `interruptedByRestart`) when a goal watch is pending, so goal-watching parents are not left waiting forever; the flag says it is an interruption, not a goal verdict.
- **Timed-out drain restarts by default** (the plan's wording); `--on-timeout abort` gives the stricter behaviour. The hold window (300 s) reopens admission if the deploy script dies after the verdict.
- **Legacy fallback on 404** keeps the deploy that ships B4 (old server, no `/drain`) guarded by the old pre-flight.
- **Lock re-entrancy** via `PI_WEB_UI_PRODUCTION_LOCK_HELD` (inherited only by descendants) lets `production:drain-restart` run inside the documented locked deploy block.

## Not done, and why

- **`/capacity` does not expose the draining state** — lane b2 owns that (brief). `GET /api/v1/drain` exposes it meanwhile.
- **`scripts/restart-pi-web-ui.sh`** (used by the Command Code weekly refresh with a 60 s timeout) keeps its own active-turn refusal rather than draining; only a one-line marker was added so the lock wrapper does not route it a second time. Converting it needs a decision about the weekly job's timeout budget.
- **Browser (P0) turns and goal-engine auto-continuations are not counted by the settle wait**: they are not admission-metered today (documented in `INTERNAL-API.md`, "Execution capacity"). The drain waits on what admission and receipts can see.
- **No production restart or deploy** (parent's job).

## Residual risks

- A run that finishes in the seconds between the drain verdict and the kill ends `completed` but is still listed in the audit's `cut_off_runs`; boot classification uses the receipt's actual state, so the receipt is right and only the audit list is conservative.
- `onFire` wakes refused during a drain (for children that end *during* the drain) are retried only within the existing bounded transient retry; the firing itself stays in the ledger.
- Rolling back to a pre-1.51.0 build makes its store reject receipts with `interruptionReason: drain_timeout` (logged and skipped at load).
- The pre-tool command gate on this host pattern-matches restart script names in command text; the live proof invoked the scripts from a driver process against a disposable unit only, with the production-target assertion described above.
