## 1. What the brief asked

Plan §6 J3 / the frozen brief: before the 2026-10-02 06:54 UTC deploy, `/capacity` reported `activeTurns: 1` (class P2) from ~06:35 while no session was busy, the drain counted 0 turns / 0 nonterminal runs, and A2's own `activeTurns` read 0 throughout (A2 took its counts from operational metrics; no admission source was wired). A permit that is never released shrinks capacity silently until a restart. Build a **detector**: A2 records admission's per-class active counts next to the runtime busy/active count; an alert (A2's existing alert path, hysteresis style) fires when they disagree for N consecutive readings and recovers once; the alert names the classes and the oldest permit's age **if admission exposes it — otherwise record what it exposes and say so**; bounded row size; no wire change.

## 2. What admission actually exposes (recorded, as the brief requires)

The sampler's source is the read-only `AdmissionController.activeCounts()` (added in correction 02 — the **only** change to `admission-controller.ts`, parent-approved for that method alone), which exposes per-class counts (`classes`, P0–P3), per-runtime counts (`runtimes`) and the total as copies of the in-memory counters. `snapshot()` is **not** side-effect free — it evaluates pressure (`evaluateHeap()` sets/clears the heap latch) and re-reads cgroup/PID/host sources synchronously — which is exactly why the detector must not sample it. `AdmissionSnapshot.oldestActiveRunStartedAt` is **declared in the interface but never populated by the controller** — it is overlaid at the `/capacity` route layer from the receipt manager (`sessions.ts:8483`), and it is receipt-derived, so it is empty in exactly the leak case (a leaked permit holds no receipt; confirmed live: the wired row carries no `admissionOldestActiveRunStartedAt`). The reading therefore records it whenever the wired source exposes it, and the alert names instead the **disagreement's own age** (incident start → end, from the incident grouping) plus a `no receipt-derived active run (a leaked permit holds no receipt)` clause — the strongest attribution admission's surface allows without touching admission beyond the approved getter.

## 3. Design (and why it cannot flap on turn boundaries)

- **One-sided on purpose.** Admission holding *more* active turns than the runtime telemetry is the leak direction. The reverse happens legitimately: receipts can be joined to another turn's permit (`sessions.ts:4035` — "must not acquire a second execution permit"), and goal-engine/extension-driven turns hold no admission slot and no receipt (B4.1). Excess = worst of (admission total − telemetry total) and any per-runtime (admission − telemetry) difference, so a totals-agree/per-runtime-disagree state is still caught; the negative direction never counts.
- **Populations agree in steady state.** Every production `admission.acquire` site pairs with a run receipt (`attachLease`), and the receipt manager releases the lease at terminalize — so admission's active count and the receipt-derived operational count (`accepted − terminal`) count the same turns. The only legitimate admission>telemetry windows are (a) turn-boundary async hops (acquire → `recordTurnAccepted`; terminalize → release) — event-loop scale, at most one sampler reading — and (b) the §11 quarantine fence (cancel/fail with unconfirmed cessation holds the lease at most `DEFAULT_DRAIN_TIMEOUT_MS` = 30 s past terminalise).
- **N = 3 consecutive readings (default), R = 2 for recovery.** At the production cadence (`OBSERVABILITY_METRICS_INTERVAL_MS` default 30 000 ms), three consecutive readings ≈ 90 s of sustained disagreement — 3× the quarantine cap and far past any boundary race — while the 2026-10-02 incident persisted ≥ 19 minutes (≈ 38 readings). A single disagreeing reading resets both the arm run and (while armed) the recovery run; recovery requires R consecutive agreeing readings at the evaluator layer. Both knobs are configurable (`OBSERVABILITY_HEALTH_ALERT_TURN_MISMATCH_READINGS/_RECOVERY_READINGS`).
- **Existing alert path.** New kind `turn_count_mismatch` flows through the existing `HealthAlertEvaluator` → `HealthIncidentGrouper` → sink chain. The grouper's per-kind debounce for this kind defaults to the evaluator's N (not the shared debounce knob), so the operator page lands exactly at the Nth disagreeing reading and a lone boundary-race reading after a close can never open a new incident on its own. Quiet period and cooldown keep their defaults (a second leak within the 30-min cooldown reopens silently and says so on recovery — the journal line still fires).
- **Row size is bounded and measured.** The fields are *absent* (not null) when admission is unwired — `JSON.stringify` drops them, so unwired rows grow by **0 bytes**. Wired rows: corrected figures in §9 (max **+170 bytes** of admission fields per row, recomputed from the retained live samples).
- **No wire change.** The metrics file is a host file, not the Internal API contract; no route, event or client-visible shape changed. Contract stays 1.58.5; the Agent OS mirror needs nothing.

## 7. Blind spots (what this detector does NOT see)

- **A stuck permit that admission and the receipts agree on** (e.g. a receipt that never terminalises) produces *agreement*, not a mismatch — that class is the drain/watchdog's territory, not a count drift. This detector only catches admission>telemetry drift (permit without a live turn).
- **Detection latency** is ≈ N×interval (≈ 90 s at production defaults) plus the quiet period on the recovery notification (10 min default) — an instance is attributed after the fact, not prevented.
- **A sustained cancel/quarantine storm** (back-to-back cancels with unconfirmed cessation, each holding ≤ 30 s) could chain past 90 s and page once; the message names the state so an operator can see receipts are terminal. Not observed in any arm.
- **Cooldown:** a second leak incident inside 30 min of a recovered one reopens silently (existing grouping style); the journal line and the metrics file still record it.
- **Single-process truth:** the source is the in-process controller; a multi-server deployment would need per-process wiring (not this product's shape).
