## 1. What the A2 telemetry can and cannot say

`~/.pi-web-ui/metrics/health-metrics.jsonl` records, every 30 s, event-loop lag percentiles
over a trailing 60 s window (500 ms sampling), plus `activeTurns` and `residentSessions`.
It says *that* the loop stalled. It cannot say *what* was on the loop. B1.2's job was to
turn the correlation (spike minutes coincide with session activity) into attribution.

## 5. Attribution (the named operation)

**Dominant operation: `PiService.createSession` → `createSessionResourceLoader(cwd)` →
`DefaultResourceLoader.reload()` → extension module loading, once per session open.**

Span evidence: 55 `pi.session.resource_loader` spans of 308–569 ms (run 2), each inside a
`pi.multi.rehydrate_session` that the sampler recorded as a 400–535 ms loop stall; in the
confirmation run, 53 recorded stalls name `pi.session.resource_loader` directly in
`blockedBy`, i.e. the instant the tick was due falls inside that span's measured window.

Mechanism (read from the SDK, then measured): `PiService.createSession` builds a **new**
`DefaultResourceLoader` and `await loader.reload()` for every session
(`server/src/pi/pi-service.ts`), and `loadExtensionsCached` keys its module cache by cwd —
`useExtensionCacheCwd()` **clears the whole extension cache whenever the cwd differs**
(`node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/loader.js`). Production
opens sessions across many distinct cwds (worktrees, scratchpads), so nearly every open is
a cache miss that re-transpiles ~780 KB of TypeScript across 16 extension entries with
`moduleCache: false` through jiti.

Direct measurement outside the server (`node`, no model calls, 16 extension entries):

| cwd | wall | CPU | 30 ms timer armed during the load |
|---|---|---|---|
| same cwd again (cache hit) | 145–183 ms | 217 ms | fired only after the load |
| different cwd (cache cleared) | 440–545 ms | 552–690 ms | fired only after the load |
| first load of the process | 1,677 ms | 1,955 ms | fired only after the load |

The "fired only after" column is the event-loop proof: the 30 ms timer was still unfired
when the load returned, i.e. the load ran as a single macrotask with no timer phase. The
control (a 120 ms synchronous busy-wait) delayed the same timer to 121 ms, so the probe
detects stalls.

Secondary costs, measured but not dominant: `pi.browser.load_session_messages` (JSONL
read + history projection) produced 42 stalls of 50–116 ms; unattributed `<none>` stalls
were 50–58 ms (sampler jitter and short unrelated blocks).

## 6. Proposed fix (implemented in Phase B — see §10)

Cache the resource loader per cwd in `PiService` and skip `reload()` for a cwd whose loader
is already loaded (`Map<string, DefaultResourceLoader>`, bounded), so a session open in a
known cwd does no extension work at all; and keep the first-open cost for a genuinely new
cwd. Alternatives considered: warming a single shared loader with per-session project
context merged (wrong — cwd changes project context/skills); moving extension load to a
worker (large; the SDK's loader is not worker-shaped); streaming session replay (a
different, smaller cost).

Risk: extension factory state would be shared between sessions in the same cwd (it is
already shared today among anything reusing `PiService.resourceLoader`), so the fix must
be proven with the existing extension/UX tests plus the reproduction. A loader lifecycle
bound (evict idle cwds) is part of the proposal. Parent approval of the exact file set is
requested in `01-attribution.md`.

> **Superseded at the phase gate.** The parent rejected the per-cwd loader cache on
> correctness (sharing `extensionsResult.runtime` makes `bindCore` route one session's
> extension actions into another) and approved a process-level **factory** cache instead;
> see §10. Kept here so the rejected design and its reasoning are recorded.

## 9. Residual risks

- The synthetic corpus is 50 MB, not production's 786 MB, and 243 generated cwds rather than
  production's exact cwd set. A size-sensitive replay cost is therefore under-represented;
  the `pi.session.open_file` / `pi.browser.load_session_messages` spans cover it separately.
- The reproduction's pre-fix p99 (≤ 533 ms) is below production's 919 ms maximum; the
  mechanism (extension load per distinct cwd) is the same, but a larger/slower store could
  add replay cost on top.
- The log-line counts are rate-limited (one per label per 5 s) and are lower bounds, not
  counts of stalls; the A2 metrics are the unbounded measure.
- `blockedBy` uses a 32-span ring: a blocking span evicted before the overdue tick runs
  would be missed. With 25 ms ticks and ~500 ms spans this does not happen in the recorded
  runs, but it is a bound, not a guarantee.

# Phase B — the fix (Option B: additive SDK accessor + factory cache)

## 10. What was built and why this design

The parent rejected the per-cwd loader cache from §6 (`01-answer.md`): `AgentSession` builds
`new ExtensionRunner(extensionsResult.extensions, extensionsResult.runtime, …)` and
`bindCore` installs the session's actions **on that runtime**, so two sessions sharing one
loaded loader share one runtime and each `bindCore` rebinds the other's actions. The parent
also rejected the private deep-import route (Option A) because
`createExtensionAPI(extension, runtime, cwd, eventBus)` bakes the init cwd into the
Extension API — `pi.exec` defaults to it (`loader.js` `exec(command, args, options) →
options?.cwd ?? cwd`) — so loading every session's extensions with a constant cwd would run
commands in the wrong directory.

The approved design: import each global extension's default-export **factory** once per
process, and let every session initialise its own runtime from it.

- **`scripts/patch-pi-coding-agent-extension-factory.mjs`** (new, postinstall-chained) adds
  two additive exports to `@earendil-works/pi-coding-agent` 0.87.1:
  - `importExtensionFactory(path)` — the SDK's private `loadExtensionModule`;
  - `seedExtensionFactory(path, factory, cwd)` — places an already-imported factory into the
    SDK's **own** module cache for that cwd, using the SDK's own
    `useExtensionCacheCwd`/`extensionCache`. `loadExtensionsCached` then reuses the factory
    while still calling `initializeExtension` per load, so each session keeps its own
    `Extension` objects and its own runtime.
- **`server/src/pi/extension-factory-cache.ts`** (new): one factory per discovered global
  extension path (`<agentDir>/extensions`, discovery mirroring the SDK's
  `discoverExtensionsInDir`), invalidated when the entry file changes or — for
  directory-shaped extensions — when any file in that directory changes; bounded (512-entry
  directory-scan cap), pruned on removal, inert when the patch is absent.
- **`server/src/pi/pi-service.ts`**: `createSessionResourceLoader` seeds the cache for the
  session's real cwd before `loader.reload()`. Nothing else in the loader path changes:
  discovery, ordering, paths, metadata, project-local/configured/package extensions, skills,
  prompts, themes and project context all run exactly as before, per real cwd.
- **`docs/ARCHITECTURE.md`**: a short note on the cache and the patch.

**Why seeding rather than the `extensionFactories` option.** `extensionFactories` labels
inline extensions `<inline:name>`, changing `extension.path` and `sourceInfo.source`
(`inline`/`temporary` instead of `local`/`user`) — a behaviour change to extension metadata.
Seeding keeps the loader's own load path, so the produced `Extension` objects are identical
to today's apart from the factory's provenance.

**Runtime fallback.** When the accessors are absent (patch not applied) the cache logs one
warning and does nothing; `createSessionResourceLoader` runs the unpatched path unchanged.
The fallback cannot throw into session creation. Both branches are tested (patched: the
isolation tests seed successfully; unpatched: the cache returns `{available:false, seeded:0}`
and never calls the seeder).

### Proposed B2 `event_loop_lag` threshold

From the post-fix distribution: steady-state A2 p99 65–96 ms, whole-load max p99 279 ms
(first-window warm-up). The existing A2 lag alert band is 500 ms high / 200 ms low
(`OBSERVABILITY_HEALTH_ALERT_LAG_P99_MS`) and is *not* changed here.

Recommended B2 `event_loop_lag` threshold: **300 ms sustained** (two consecutive readings
above it), with recovery at **150 ms**. Rationale: 300 ms is the production spike boundary
the plan already uses (17–18 spike minutes in 22 h), the pre-fix build reaches it in every
window under this load, and the post-fix build does not reach it at all (max 279 ms). A
lower threshold (e.g. 150 ms) would refuse API work during the residual per-session
initialisation that this lane explicitly left unaddressed, so it is not proposed.

## 14. Not done and why (Phase B)

- Lazy/deferred extension initialisation — explicitly out of scope per `02-answer.md`; the
  residual span is named in §12 as an R2 follow-up.
- Project-local/configured/package extension caching — they are cwd-dependent and stay on
  the loader's per-cwd path (requirement 2 is the only guarantee).
- Making `session.reload()` reuse the cache: `DefaultResourceLoader.reload()` on a loaded
  loader calls `clearExtensionCache()` itself, so a reload re-imports. Correctness holds
  (requirement 3's reload path), speed does not; documented rather than worked around.

## 15. Residual risks (Phase B)

- The patch edits `node_modules`; it is guarded, idempotent and loud on change, and the
  runtime falls back without it — but an SDK upgrade requires re-evaluating it (as with the
  pi-ai patch).
- `useExtensionCacheCwd` clears the SDK cache on every cwd change, so every session still
  pays 16 cache-writes plus per-session `initializeExtension`; that is the residual in §12.
- A global extension added while the process runs is picked up on the next session (our
  discovery re-reads the directory each load and fingerprints it).
- Isolation is proven at the loader/runner/runtime level and in the live client check; the
  parent's independent re-run is the acceptance step.

### Major 1 — caching an evaluated module shares its module-scope state

### Major 2 — seed → reload is not atomic against the SDK's single global cwd slot

Concurrent opens in cwd A and cwd B could interleave: B's seed clears A's entries and A's load
clears B's, so both re-import on the loop. `runExtensionLoadCriticalSection` now serialises the
whole seed → `loader.reload()` interval process-wide (`pi-service.createSessionResourceLoader`).

Tests: the critical section runs tasks strictly in submission order and survives a rejection; at the
loader level, concurrent different-cwd loads serialise (`enter:A, exit:A, enter:B, exit:B`) with one
import per path, while an explicit unprotected control interleaves (`enter:A, enter:B, …`) — the
hazard the section removes.

4. **Traversal budget** now bounds directories (`maxScanDirs`, default 128) as well as entries

### How much of the improvement survives the allowlist — almost none

Denying the six per-session-state extensions (47 % of the transpiled bytes; `subagent` 155 KB,
`goal-engine` 121 KB, `enhanced-plan-mode` 101 KB are the largest) puts A2 p99 back at 329–686 ms
with **6 spike minutes — the same count as the pre-fix control**, and `resource_loader` back to
p50 388 ms (first pass 113 ms). A paired probe on this host, under the same conditions and timing
only `loader.reload()` (seed/import outside the timed section), isolates the cause:

| Seeded | reload (3 cwds) |
|---|---|
| all 16 extensions | 397 / 280 / 283 ms |
| allowlist (10) | 534 / 655 / 631 ms |

Not caching the six costs ~250–350 ms more per open. So the allowlist is the cause of the
regression, and the mutex is not: it only orders the same work. The honest result is that **the
corrected fix does not remove the stall**. The safety requirements of the review are met; the
performance purpose of B1.2 is not.

### What this means for B2's `event_loop_lag` threshold

From this final distribution, browser session-opening alone reaches A2 p99 686 ms. No threshold
below ~700 ms can separate "browser activity" from "API risk" with this fix, so a 300 ms gate — the
value proposed before the correction — would refuse API work because of browser activity, which is
precisely the failure the plan warned about. **Do not set B2's threshold from this distribution.**
Keep A2's existing 500 ms / 200 ms alert band, and treat B1.2's separation goal as not met.
