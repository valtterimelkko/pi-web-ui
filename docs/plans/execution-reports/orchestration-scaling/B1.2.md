## 1. What the A2 telemetry can and cannot say

`~/.pi-web-ui/metrics/health-metrics.jsonl` records, every 30 s, event-loop lag percentiles
over a trailing 60 s window (500 ms sampling), plus `activeTurns` and `residentSessions`.
It says *that* the loop stalled. It cannot say *what* was on the loop. B1.2's job was to
turn the correlation (spike minutes coincide with session activity) into attribution.

## 3. Instrumentation

`server/src/observability/loop-stall-attribution.ts` (new), wired at the session-open call
sites in `server/src/pi/pi-service.ts`, `server/src/pi/multi-session-manager.ts` and
`server/src/websocket/connection.ts`, plus a section in `docs/OBSERVABILITY.md`.

- named spans (`span` sync, `spanAsync` awaited): `pi.service.initialize`,
  `pi.session.open_file`, `pi.session.create_file`, `pi.session.resource_loader`,
  `pi.session.create_agent_session`, `pi.multi.create_session`,
  `pi.multi.rehydrate_session`, `pi.browser.load_session_messages`;
- a 25 ms self-rescheduling sampler that measures how late each tick ran; a tick ≥ 50 ms
  late is a recorded stall, attributed to the innermost active label **and** to every
  recently-completed span whose measured window contains the instant the tick was due
  (`blockedBy` — the direct blocker evidence, since the overdue tick can only run after the
  blocking span exits);
- over-threshold spans (≥ 100 ms) and stalls are logged (rate-limited to one line per label
  per 5 s) through the central logger, so they land in the diagnostics ring buffer
  (`GET /api/v1/diagnostics?component=LoopAttribution`);
- bounded: 50-record stall ring, 50-record span ring, 32-record recent-span ring, 64-label
  cardinality cap (overflow → `<other>`), `unref()`'d timer, inert logger under `VITEST`.
  Snapshot accessor `readLoopStallAttribution()` never creates or starts anything.

TDD: `server/tests/unit/observability/loop-stall-attribution.test.ts` — 20 tests.

- RED: `NODE_ENV=test npx vitest run tests/unit/observability/loop-stall-attribution.test.ts`

## 5. Attribution (the named operation)

**Dominant operation: `PiService.createSession` → `createSessionResourceLoader(cwd)` →
`DefaultResourceLoader.reload()` → extension module loading, once per session open.**

Span evidence: 55 `pi.session.resource_loader` spans of 308–569 ms, each inside a
`pi.multi.rehydrate_session` that the sampler recorded as a 400–535 ms loop stall (window
overlap, i.e. the stall's due instant falls inside the span's measured window).

Mechanism (read from the SDK, then measured): `PiService.createSession` builds a **new**
`DefaultResourceLoader` and `await loader.reload()` for every session
(`server/src/pi/pi-service.ts`), and `loadExtensionsCached` keys its module cache by cwd —
`useExtensionCacheCwd()` **clears the whole extension cache whenever the cwd differs**
(`node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/loader.js`). Production
opens sessions across many distinct cwds (worktrees, scratchpads), so nearly every open is
a cache miss that re-transpiles ~780 KB of TypeScript across 16 extension entries with
`moduleCache: false` through jiti.

Direct measurement outside the server (`node`, no model calls, 16 extension entries):

| cwd | wall | CPU | 30 ms timer armed during the load |
|---|---|---|---|
| same cwd again (cache hit) | 145–183 ms | 217 ms | fired only after the load |
| different cwd (cache cleared) | 440–545 ms | 552–690 ms | fired only after the load |
| first load of the process | 1,677 ms | 1,955 ms | fired only after the load |

The "fired only after" column is the event-loop proof: the 30 ms timer was still unfired
when the load returned, i.e. the load ran as a single macrotask with no timer phase. The
control (a 120 ms synchronous busy-wait) delayed the same timer to 121 ms, so the probe
detects stalls.

Secondary costs, measured but not dominant: `pi.browser.load_session_messages` (JSONL
read + history projection) produced 42 stalls of 50–116 ms; unattributed `<none>` stalls
were 50–58 ms (sampler jitter and short unrelated blocks).

## 6. Proposed fix (for the phase gate; not implemented)

Cache the resource loader per cwd in `PiService` and skip `reload()` for a cwd whose loader
is already loaded (`Map<string, DefaultResourceLoader>`, bounded), so a session open in a
known cwd does no extension work at all; and keep the first-open cost for a genuinely new
cwd. Alternatives considered: warming a single shared loader with per-session project
context merged (wrong — cwd changes project context/skills); moving extension load to a
worker (large; the SDK's loader is not worker-shaped); streaming session replay (a
different, smaller cost).

Risk: extension factory state would be shared between sessions in the same cwd (it is
already shared today among anything reusing `PiService.resourceLoader`), so the fix must
be proven with the existing extension/UX tests plus the reproduction. A loader lifecycle
bound (evict idle cwds) is part of the proposal. Parent approval of the exact file set is
requested in `01-attribution.md`.

## 9. Residual risks

- The synthetic corpus is 50 MB, not production's 786 MB, and 243 generated cwds rather than
  production's exact cwd set. A size-sensitive replay cost is therefore under-represented;
  the `pi.session.open_file` / `pi.browser.load_session_messages` spans cover it separately.
- The reproduction's p99 (≤ 533 ms) is below production's 919 ms maximum; the mechanism
  (extension load per distinct cwd) is the same, but a larger/slower store could add replay
  cost on top.
- The log-line counts are rate-limited (one per label per 5 s) and are lower bounds, not
  counts of stalls; the A2 metrics are the unbounded measure.
- `blockedBy` uses a 32-span ring: a blocking span evicted before the overdue tick runs
  would be missed. With 25 ms ticks and ~500 ms spans this does not happen in the recorded
  runs, but it is a bound, not a guarantee.
