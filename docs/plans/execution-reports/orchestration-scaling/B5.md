## 1. What was fixed

F1 (R2): Pi Web UI never emitted `session_shutdown` when it disposed a Pi session — only the CLI's new/resume/fork/quit/reload did (`AgentSessionRuntime.dispose`, `teardownCurrent`, `AgentSession.reload`). Nine of sixteen deployed extensions clean up only in that handler, so on every Web UI dispose: background-shell processes outlived the session (live-confirmed by lane v2b on master: a `sleep 1234` started by a child survived DELETE, same pids and cgroup 15 s later), goal-engine continuation and watch-wake poll timers stayed armed, memory did not save, auto-compact-75 heartbeats kept running.

Every dispose/unload path now routes through **one funnel** (`MultiSessionManager.teardownOnce`, per-path in-flight map) that emits **one bounded `session_shutdown`** through the SDK's public `AgentSession.extensionRunner` (`hasHandlers` → `emit`) **before** `agentSession.dispose()` — the SDK's own `teardownCurrent` order (emit → dispose). No upstream changes (owner rule); the non-exported `emitSessionShutdownEvent` helper is not deep-imported.

- **Paths wired (all emitting exactly once, funnel-deduped under races):** manager — `disposeLoadedSession` (Internal API DELETE, aggressive cleanup, stale-stream reset), `unloadSession` (idle timeout, error cleanup, maxSessions eviction), `stopSession` (now funnel kind `stop`), failed-create cleanup, `dispose()` (server shutdown; emissions parallel within one bound). PiService — `createSession` bind-failure catch, `removeClient` (last owner), `cleanup()`.
- **Reason mapping:** everything terminal → `quit`. One exception: `recoverSession` (dispose→rehydrate of the same file) emits `resume` + `targetSessionFile` so the successor runtime adopts extension state exactly like a CLI session switch (background-shell keeps tasks for adoption, memory saves) — this also preserves today's live behaviour on that path while adding timer/handle release, and turns the previously-drifting settle comment (v2b drift note, `multi-session-manager.ts:709-710`) into accurate awaited behaviour. Idle unload uses `quit` deliberately: the extension runtime is genuinely torn down and rehydration is not guaranteed, so keeping processes/timers alive on the off-chance would preserve the very leak the event closes; persisted extension state reconciles truthfully on a later rehydration.
- **Bound & safety:** `sessionShutdownTimeoutMs` option (default 5 s = background-shell's own teardown budget); a hanging emission loses the race and disposal proceeds; handler errors are caught and logged (the SDK already routes handler exceptions to its error listeners); sessions without shutdown handlers skip emission entirely (zero added latency).
- **Caller wiring:** `disposeLoadedSession` became `Promise<boolean>`; all six Internal API callers now `await` it so the bounded emission and final flush complete **before the backing JSONL is unlinked** (a late flush would resurrect a deleted session). `connection.close()` awaits `manager.dispose()`.

New module: `server/src/pi/session-shutdown.ts` (public-API emission helper only).

## 6. Audit — shutdown handlers vs validation children (brief requirement)

## 7. Blind spots (what this mechanism does NOT see or cover)

- **`SessionPool` dispose sites are NOT wired** (`server/src/pi/session-pool.ts` lines ~45, ~86, ~148: extension-driven `createClientSession`/`switchClientSession` replacement and pool `removeClient`). The pool is outside this lane's owned paths (brief: `multi-session-manager.ts`, `pi-service.ts`, "any new module next to them"); the parent should adjudicate — the natural mapping is `new`/`resume` for the replacement paths and `quit` for pool teardown, mirroring the CLI switches those paths imitate. `piService.cleanup()` drains the pool first, so pool-disposed sessions are simply absent from the remaining-sessions emission (no double-emit today — and also no emit at all).
- **`SessionDisposalRegistry`** (`server/src/internal-api/session-disposal.ts`) runs pi-web-ui-side handles only; it never sees `AgentSession`s and needs no emission.
- **Timers that extensions arm outside their `session_shutdown` reach** (e.g. `setTimeout` handles captured elsewhere) are the extensions' own responsibility; B5 guarantees the event fires, not what every handler does.
- **The 5 s bound is per emission, sequential per session in a sweep pass** (`Promise.all` across sessions in a pass, so a sweep's wall-clock bound is one bound, not N); a path-by-path worst case (single DELETE) is one bound.
- **The live proof observes absence** (processes gone, no turns, silent journal). It cannot prove a handler *started* and finished cleanly — only that its effects landed (processes dead) and nothing fired afterwards.
- **Delete-latency change is real but unmeasured in production terms:** a DELETE of a handler-laden session can now take up to ~5 s longer. The two probe DELETEs returned 200 in ~1 s each (handlers settle fast when idle). No contract bump because shapes are unchanged; flagging for the parent in case the orchestration client's DELETE timeout needs headroom.

## 8. Residual risks

- An extension whose shutdown handler **ignores** its own deadline could still hold disposal up to the 5 s bound per dispose — bounded, logged, never unbounded.
- `stopSession` now shares the funnel: a stop racing a cleanup-sweep unload awaits the same teardown and reports `true`. Callers treating `true` as "I disposed it synchronously" would be wrong only in timing, not effect.
- The recovery path's `resume` emission keeps background-shell tasks alive across rehydration — same as pre-B5 live behaviour, but now memory also saves on that path (new write). Validation-isolated by fake HOME; production impact is a session-memory save on recovery, which is the extension's designed behaviour on any switch.
