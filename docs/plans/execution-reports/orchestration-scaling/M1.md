## What this delivers

The Agent OS mirror of the Pi Web UI Internal API contract was hand-maintained
and updated only when someone remembered (agent-os `15bda8d` 1.56.0, `d9aea11`
1.58.0). M1 makes the sync mechanical and visible to a bumping agent:

1. a cross-repo sync test that fails on any drift and skips cleanly when the
   Pi Web UI checkout is absent;
2. an `agent-os health` **warning** (`PI_WEB_UI_CONTRACT_MIRROR_STALE`) when the
   mirror is behind — guidance, never an error or a refusal;
3. a written procedure in both repositories, where a bumping agent reads it.

No Pi Web UI wire change, so `INTERNAL_API_CONTRACT_VERSION` stays at **1.58.0**
and the Agent OS mirror versions are unchanged (they already match).

## DESIGN DECISIONS

- **A shared reader module** (`src/pi-web-ui/contract-mirror.ts`) rather than a
  parser duplicated inside the test: the test and the health warning consume the
  same `checkContractMirror`, so they cannot disagree about what "drift" means.
- **A warning, not an error or a gate.** The mirror is a repo-maintenance
  concern; making `agent-os health` fail on it would be a new refusal path, which
  the brief's standing policy forbids. The signal is a `warning`, so a bumping
  agent sees it while no routine path breaks.
- **`PI_WEB_UI_REPO` first, then the existing `AGENT_OS_PI_WEB_UI_REPO_ROOT`
  convention, then `/root/pi-web-ui`** — the brief names `PI_WEB_UI_REPO`; the
  other two are honoured so the helper agrees with `src/config.ts`.
- **The changelog requirement is a real assertion**: the exact historical
  failure was a version served without a mirror changelog entry, so the check
  requires a `> - \`X.Y.Z\`` entry, not merely a version string somewhere.
- **Test the health wiring through `runHealthCheck`**, not just the pure helper,
  so the finding code and severity are proven on the real path.

## BLIND SPOTS (what this mechanism does NOT see)

- It compares **version strings and the presence of a changelog entry**; it does
  NOT judge whether the mirror's *prose* correctly describes a given bump. A bump
  that updates all four markers but writes a wrong description still passes. The
  Pi Web UI `contract-version-drift` test covers the reverse direction for the
  Pi Web UI doc only.
- It reads the checkout at `PI_WEB_UI_REPO` / `AGENT_OS_PI_WEB_UI_REPO_ROOT` /
  `/root/pi-web-ui`, **not** the deployed production server's reported
  `contractVersion`. A checkout that is behind production (or production behind
  the checkout) is invisible; the brief scoped this to the checkout.
- The health warning runs only where `agent-os health` runs. A bump merge that
  never runs health in the Agent OS worktree still relies on the sync test in CI
  or the reviewer.
- If the mirror files are renamed, the readers return `null` and `status`
  becomes `mirror-unreadable` (silent, no warning); the sync test would then
  report `stale`/unreadable through `checkContractMirror` only if a checkout is
  present. Renaming the three mirror files is out of scope.
- The test pin is read by regex from
  `tests/pi-web-ui-observability-contract.test.ts`; if that test's pin assert is
  reworded, the reader returns `null` (drift), which is deliberately loud.
- The check is process-local and offline; it cannot detect a *wire* change that
  was never given a version bump in the first place (that remains the
  `contract-version-drift` judgment call about whether a diff is wire-visible).

## NOT DONE AND WHY

- **No live Pi Web UI server / `validate:server`** — the m1 brief states no live
  server is needed; the change is a repo-mirror check, not runtime behaviour.
- **No Pi Web UI `npm run build`** — documentation-only change, no compiled
  artefact, no live run.
- **No agent-governor or CI wiring** — the brief scoped the signal to the sync
  test and (optionally) `agent-os health`; adding a CI job or a board gate would
  be a new gate without an owner-accepted reason.
- **No version bump / changelog entry in either contract doc** — there is no
  wire change; the Pi Web UI doc edit is deliberately doc-only with no version
  bump so the C6 stability window is unaffected.
