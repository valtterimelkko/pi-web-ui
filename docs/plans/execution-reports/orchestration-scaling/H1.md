## 3. Phase B — the change (test-first)

All in `server/src/websocket/connection.ts` (owned lane paths only; `multi-session-manager.ts`
needed no change):

1. **`PI_WEB_UI_VIEW_ONLY_SUBSCRIBE`** (`on|true|1`, default **off**, read once at start-up;
   documented in `DEPLOYMENT.md`'s env table and `.env.example`). Flag off ⇒ behaviour is
   byte-for-byte today's (the whole existing suite passes unchanged — proof below).
2. **View-only open** (`viewOnlySwitchSession`): with the flag on, a switch to a **non-resident**
   Pi session validates identity, reads the cwd header, replays the transcript from the file, and
   sends the same `session_switched` message with the session id from the canonical filename and
   **model/thinkingLevel derived from the file** (last `model_change` / `thinking_level_change`,
   falling back to the last assistant message's provider/model — the same sources the SDK's own
   session context settings read). No agent, no rehydrate, no extension loading, no skills walk,
   no resident pin. The crash-interrupted-session reconciliation and background-children snapshot
   behave exactly as on a materialising switch. The connection-side viewing map is set (that is
   what `getCurrentSessionPath` reads); the manager-side viewing registration is deliberately NOT
   set — its guard requires a subscription, and a view-only open has none (this was the first live
   proof's bug, fixed in `32b9dc1a`).
3. **On-demand materialisation** (`ensurePiAgentSession`): the first agent-requiring action —
   `prompt`, `steer`, `follow_up`, `set_model`, `set_thinking_level`, `compact`,
   `get_session_info` — materialises the agent via the existing `subscribeClient` (today's
   rehydrate), registers the manager-side viewing ref together with the new subscription, and then
   proceeds exactly as today. Concurrent first actions share one `subscribeClient` call through a
   per-path in-flight map. `abort` with no agent stays a silent no-op (as today). With the flag
   off, `ensurePiAgentSession` is exactly today's `getAgentSession` read (no subscription attempt)
   — the callers' `SESSION_NOT_FOUND` surfaces are unchanged.
4. **`handleCompact` resolver fix**: it resolved its session through the manager's *subscription*
   map while every other Pi action resolves through the connection's *viewing* map; a view-only
   open has no subscription, and for subscribed clients the two could only disagree when a
   cross-runtime switch left a stale manager subscription — where compacting the stale session
   was wrong anyway. Now uniform (`getCurrentSessionPath`, manager-map fallback preserved).
5. **sessions_list payload cache (Option 3, always on)**: the serialised frame is cached and
   reused while a cheap full change signature is unchanged — a fold over every pi entry
   (`id:messageCount:lastActivity`), the registry origins, and full folds over each runtime's list
   (small lists, folded fully so a middle-entry change cannot hide). Cache counters are exposed
   via `getSessionsListCacheStats()`. Failure semantics of each runtime list are unchanged (warn +
   continue).

## 8. Contract

No Internal API wire change: `server/src/internal-api/**` is untouched; every internal-api /
pilot / talker / transfer caller of `subscribeClient` keeps the default (materialise). The browser

## 9. Design decisions

- View-only applies **only** to the browser `switch_session` path. `subscribe_session` (worker /
  events path), the pilot WS, talker `ensureReady` and Internal API transfer keep materialising —
  they need live events or an agent, and keeping their default preserved the lane boundary
  (internal-api/** is H2s's).
- Manager-side viewing registration is deferred to materialisation (the manager's guard requires a
  subscription; there is no materialised session to dispose before that). The connection's own
  viewing map — the one `getCurrentSessionPath` reads — is set at open.
- Model/thinking come from the file's own record rather than a catalogue lookup: no agent exists,
  and the SDK's session context settings use the same sources.
- The payload cache keys on value folds, not list identity — the pi cache rebuilds arrays every
  call by design; keying on identity would never hit.

## 10. Not done and why

- No multi-tab simultaneous-burst arm (the flag-off Phase A ladder already bounds today's
  behaviour; the flag-on arms show browsing contributes ~0 regardless of duty cycle).
- No change to the WS rate limiter (60 msgs/min/client) — it refused the last 6 switches of the
  superhuman back-to-back arm; that is its designed job.
- No production rollout: the flag is off by default; the owner turns it on at an owner-approved
  restart (plan rule).
- Upstream observation not submitted (owner decision at review): see §13.

## 11. Residual risks

- With the flag on, the first prompt on a cold-viewed session pays the rehydrate (~1.2–1.7 s)
  before the turn starts — the same total work, moved to a moment where a wait is expected; the
  browser shows the normal "awaiting" state during it (screenshots 04 show streamed replies).
- Startup-emitting extensions' status widgets appear on first prompt instead of at open (§6).
- Concurrent API-side **creates** remain the one measured same-class lag spike (§4); G4's
  upstream seam is the path to removing it.
- `get_sessions` still pays the mtime walk and the socket write per call (§4).

## 12. Blind spots (what this evidence does NOT see)

1. The browsing-only gate latch was not replayed bit-exactly on the quiet disposable host (peak
   289 vs production 342–383); the same-mechanism latch (create burst, 451×2) was. The fix removes
   the mechanism itself, so the delta does not change the conclusion, but the exact production
   reproduction remains unproven.
2. Switch targets up to ~335 KB / 313 entries; larger real transcripts raise the *viewing* share
   (kept by design) — unmeasured above that size.
3. The browser proof ran headless Chromium through the vite dev client (the validation server
   cannot serve the UI itself); a headed browser on the owner's machine may drain sockets and
   render differently (the 2,068-row sidebar renders fine headless, screenshots captured).
4. One Playwright run was driven against a stale dev-server proxy by a harness mistake (killed and
   re-run cleanly); all published screenshots come from the clean runs.
5. The flag-on arms ran on a host shared with sibling lanes (h2s live validation was active
   during some arms) — numbers are therefore if anything pessimistic.

## 13. Upstream robustness observation (no code change in this lane)

A hand-written **v1-shaped** session file (no `version` header, no entry `id`s — a shape the SDK
itself never writes; production: 0 of 870 files lack a version header, checked by the parent) drove
the SDK's open/migration path into a 4 GB heap OOM that killed a disposable server during an early
Phase A arm (retained in the lane's run directory's server log: "Ineffective mark-compacts near heap limit",
uptime 117 s). Reproduction: seed a session file whose header lacks `version` with a few hundred
`type:"message"` entries lacking `id`/`parentId`, then `switch_session` to it. Real v3-shaped
files (including this lane's 313-entry extensions) open cleanly (RSS 511→592 MB on a single
switch). Filed here for the owner's upstream decision; H1 does not depend on it.
