## What was fixed

1. **Stale `dist` guard.** New `server/src/live-validation/heap-soak/build-freshness.ts`
   (pure) + `scripts/heap-soak/build-freshness-io.ts` (git/stat I/O). The launcher
   checks before it creates any directory or unit and **refuses** to start when:
   no compiled artefact exists; `server/src`/`shared/src` is dirty; the oldest
   compiled-artefact mtime is older than the newest commit touching those trees
   (`git log -1 --format=%ct -- server/src shared/src` — no build-script
   change); or the git state cannot be read. Checkout HEAD + the check result
   are written to `run-state.json` and rendered at the top of `report.md`.
   **Choice recorded:** refuse, with no `--rebuild` flag — a rebuild the harness
   performs itself would make the `dist` under test different from the commit
   the operator reviewed; `npm run build` is the explicit fix.
2. **End snapshot.** `snapshotOffsetsMs` declared an offset equal to `totalMs`,
   but the sampler loop exits on `isRunComplete(elapsed >= totalMs)` first, so
   it never fired. `phases.ts` now splits the offsets into
   `interimSnapshotOffsetsMs` (strictly inside the window, used by the sampler)
   and `endSnapshotOffsetMs` (the window length). The supervisor takes the end
   snapshot after the window closes and before finalisation, with a forced GC
   first, records it in run-state, and the report's start-vs-end snapshot
   comparison (existing fallback to the latest valid snapshot) plus the retainer
   summary therefore use the real end heap.
3. **Teardown.** The supervisor stops the disposable server at completion,
   after the end snapshot, before it exits. `--keep-server` /
   `HEAP_SOAK_KEEP_SERVER=1` keeps it up, and the completion Telegram body then
   says `SERVER LEFT RUNNING` (pure `completionNoticeBody`). `server_died`
   handling is untouched: a dead run still ends as `server_died` with its death
   evidence and is never reclassified.
4. **Orphan-sweep race.** The driver tracks session ids whose `runChild` call is
   still executing (`DriverState.inFlight`); the sweep skips them
   (`partitionSweepCandidates`). If a swept session nevertheless fails later, the
   driver records it as `orphan_swept`, not `child_failed`
   (`classifyChildFailure`). `report.md` reports "swept children mis-counted as
   child failures" (`sweptChildFailures`), which a correct run leaves at 0.
   **Choice recorded:** both halves — skip in-flight (removes the race) and
   re-attribute (so the accounting cannot regress if a sweep ever races a
   straggler the tracker missed).
5. **Bounded run length.** `start --hours <n>` (whole number, 1–168; default
   24) scales `totalMs`; checkpoints and snapshot offsets are fractions of
   `totalMs`, so both scale. `fullRunPlan` + `cli.ts plan [--hours <n>]` is the
   dry run; `run-state.json` records `windowHours` and `report.md` renders it.
   The wave loop now also stops at the window bound (`isStopped` includes
   `isRunComplete`), so a bounded run is actually bounded.

## Residual risks

- **Sweep-skip vs a permanently hung child.** The sweep now skips any session an
  in-flight `runChild` still owns. `promptStream` has a request timeout, so a
  straggler eventually settles and deletes its own session, but a child that
  hangs longer than that timeout is no longer swept early. The re-attribution
  half (`classifyChildFailure`) keeps the accounting honest, and the report's
  "swept children mis-counted" invariant stays measurable. In the micro run the
  sweep skipped 5–6 in-flight sessions per cycle and still swept all 7 true
  orphans (including the deliberate leak) — so the skip did not starve the
  sweep at this load.
- **`--hours` window vs a long wave.** The wave loop is now bounded by the
  window, but in-flight stragglers still settle in the background after the
  window (by design — they are real sessions); for very short windows the end
  snapshot may therefore include recently-completed children.
- **`git log -1 -- server/src shared/src` uses the committer date.** A rebase or
  a commit with a rewritten/backdated committer timestamp could make a fresh
  build look stale (refusal is the safe direction) or, in principle, a stale
  build look fresh (a backdated commit); the guard's normal case — build after
  commit — is unaffected.
- The stale-build guard is mtime-based, not content-based: a `dist` rebuilt from
  the same source but then left while a *newer* commit with the same second
  lands is accepted at equal second granularity (test covers the equality case
  deliberately).
- **Micro-run observation, not a B0.1 finding.** The end-snapshot retainer
  summary names `AgentSession` (5 instances via
  `object:global / --property:__PIWEBUI_LOGGER__-->`). At the end of a micro run
  stragglers are still in flight, so a handful of live sessions is expected; it
  is an A1/B1 question whether any of those are disposed-and-retained, not a
  B0.1 one. Flagged here so it is not later mistaken for new evidence.
- **Micro-run sample coverage 113/121 (93.4%)**, below A1's 95% target, with a
  largest gap of 1.6 intervals. A Gate 1 micro run deliberately `SIGKILL`s the
  supervisor mid-run (the reattach control) and takes start/end heap snapshots,
  both of which cost samples; this is not a B0.1 criterion and not a regression
  from these changes.
