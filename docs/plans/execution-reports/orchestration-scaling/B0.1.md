## What was fixed

1. **Stale `dist` guard.** New `server/src/live-validation/heap-soak/build-freshness.ts`
   (pure) + `scripts/heap-soak/build-freshness-io.ts` (git/stat I/O). The launcher
   checks before it creates any directory or unit and **refuses** to start when:
   no compiled artefact exists; `server/src`/`shared/src` is dirty; the oldest
   compiled-artefact mtime is older than the newest commit touching those trees
   (`git log -1 --format=%ct -- server/src shared/src` — no build-script
   change); or the git state cannot be read. Checkout HEAD + the check result
   are written to `run-state.json` and rendered at the top of `report.md`.
   **Choice recorded:** refuse, with no `--rebuild` flag — a rebuild the harness
   performs itself would make the `dist` under test different from the commit
   the operator reviewed; `npm run build` is the explicit fix.
2. **End snapshot.** `snapshotOffsetsMs` declared an offset equal to `totalMs`,
   but the sampler loop exits on `isRunComplete(elapsed >= totalMs)` first, so
   it never fired. `phases.ts` now splits the offsets into
   `interimSnapshotOffsetsMs` (strictly inside the window, used by the sampler)
   and `endSnapshotOffsetMs` (the window length). The supervisor takes the end
   snapshot after the window closes and before finalisation, with a forced GC
   first, records it in run-state, and the report's start-vs-end snapshot
   comparison (existing fallback to the latest valid snapshot) plus the retainer
   summary therefore use the real end heap. **Corrected 2026-09-28:** the load
   is now drained (bounded) and one final orphan sweep run before the snapshot —
   see **Correction** below.
3. **Teardown.** The supervisor stops the disposable server at completion,
   after the end snapshot, before it exits. `--keep-server` /
   `HEAP_SOAK_KEEP_SERVER=1` keeps it up, and the completion Telegram body then
   says `SERVER LEFT RUNNING` (pure `completionNoticeBody`). `server_died`
   handling is untouched: a dead run still ends as `server_died` with its death
   evidence and is never reclassified.
4. **Orphan-sweep race.** The driver tracks session ids whose `runChild` call is
   still executing (`DriverState.inFlight`); the sweep skips them
   (`partitionSweepCandidates`). If a swept session nevertheless fails later, the
   driver records it as `orphan_swept`, not `child_failed`
   (`classifyChildFailure`). `report.md` reports "swept children mis-counted as
   child failures" (`sweptChildFailures`), which a correct run leaves at 0.
   **Choice recorded:** both halves — skip in-flight (removes the race) and
   re-attribute (so the accounting cannot regress if a sweep ever races a
   straggler the tracker missed).
5. **Bounded run length.** `start --hours <n>` (whole number, 1–168; default
   24) scales `totalMs`; checkpoints and snapshot offsets are fractions of
   `totalMs`, so both scale. `fullRunPlan` + `cli.ts plan [--hours <n>]` is the
   dry run; `run-state.json` records `windowHours` and `report.md` renders it.
   The wave loop now also stops at the window bound (`isStopped` includes
   `isRunComplete`), so a bounded run is actually bounded.

## Correction (parent verification, 2026-09-28)

The parent's verification of the first micro run found a **major** defect in
item 2: the end snapshot was taken before the load had drained.

**Defect and evidence.** `micro-1790628570363-71157eb2`'s
`snapshots/snapshot-1200000ms.heapsnapshot` finished at **21:09:49.160**, but
`events.jsonl` shows children still being prompted and deleted at
21:09:49.767, 21:09:51.5, 21:09:53.7, 21:09:56.5 and 21:09:58.7. Replaying
`child_created` minus `child_deleted`/`orphan_swept` up to the snapshot's mtime
leaves **5 live children** — exactly the report's `AgentSession: 5 instance(s),
5 reachable … via PiService.sessions`. The snapshot therefore showed in-flight
children, not retention, and could not answer the plan's key criterion ("the
retainer summary shows no deleted child retained"). Cause: `isStopped: () =>
stopped || isRunComplete(...)` makes `runWave` return at the window's end while
a wave's stragglers are still mid-lifecycle, and `takeEndSnapshot()` ran
immediately.

**Fix.** `server/src/live-validation/heap-soak/end-drain.ts` (pure) + supervisor
wiring:

- `evaluateDrain` defines drained as **nothing in flight AND every created child
  has a terminal delete** (`child_deleted`/`orphan_swept`); `liveChildren` is
  the union of in-flight and open ids.
- `drainBeforeEndSnapshot()` waits, bounded by `endDrainTimeoutMs` =
  `max(waveMs, 120 s)` (micro 120 s; full 600 s), then runs **one final orphan
  sweep** (which deletes anything left no in-flight cycle owns) and re-evaluates.
  On timeout it records the still-live children instead of blocking for ever.
- Only then does `takeEndSnapshot()` force GC and snapshot. It records
  `liveChildrenAtEndSnapshot` (count), `liveChildrenAtEndSnapshotIds` (bounded to
  50) and `endSnapshotDrain {drained, timeoutMs}` in `run-state.json`.
- `computeRetainedDeletedChildren`/`renderRetentionVerdict` print, in `report.md`
  (both from the supervisor and from `cli.ts report`): the end snapshot's
  `AgentSession` count, the live count at the snapshot, the single known bounded
  extension slot by name (`subagent extension \`backgroundStatusCtx\``), and the
  verdict **`Retained deleted children: N`** where `N = max(0, AgentSessions −
  live children − known bounded slots)`.

Also cleared while in the file: the two pre-existing latent `TS2345` narrowing
errors in `supervisor.ts` (a `runStatePath` const narrowed only by an early
throw is captured by hoisted function declarations), so a manual `tsc -p` over
the harness now reports only the ad-hoc-config `import.meta`/CJS artifacts.

## Correction 04 (parent verification, 2026-09-28)

**Defect.** A session whose `createSession` is in flight when the supervisor is
killed has no `child_created` event; `sweepOrphans` reconciles only from
`events.jsonl`, so it never deletes it. The orphan then appears in the end
snapshot and is misread as retention. This can happen after any supervisor
restart in D1 or E2.

**Fix.**

- `orphans.ts` (pure): `ServerSessionRef`, `trackedSessionIds(events)`,
  `isUnderChildWorkspace(cwd, root)` and `findUntrackedChildrenSessions` — a
  server session under THIS run's `children/` root, absent from the harness's
  known ids, and past a 30 s grace window.
- `orphan-sweep.ts`: `sweepUntrackedServerSessions` lists the server's sessions
  (`GET /api/v1/sessions`, via the supervisor) and deletes each selected one as
  `orphan_swept` with `detail: untracked`, reusing `deleteSessionWithRetry`.
  Correction 03's rule is unchanged: only a confirmed not-found terminalises; a
  transient error leaves the session open.
- `supervisor.ts`: reconciliation runs on **every cycle** and once more in the
  **end drain**, before the snapshot; `run-state.json` records
  `serverChildrenSessionsAtEndSnapshot`, `untrackedServerSessionsAtEndSnapshot`
  and `untrackedOrphansSwept`.
- `report.md` reports **three figures** — live on the server (harness-known live
  + untracked), the verified known slot, and retained deleted — with
  `retained deleted = AgentSessions − live-on-server − verified slot`. A session
  the server still lists is never called retained.

## Residual risks

- **Sweep-skip vs a permanently hung child.** The sweep now skips any session an
  in-flight `runChild` still owns. `promptStream` has a request timeout, so a
  straggler eventually settles and deletes its own session, but a child that
  hangs longer than that timeout is no longer swept early. The re-attribution
  half (`classifyChildFailure`) keeps the accounting honest, and the report's
  "swept children mis-counted" invariant stays measurable. In the micro runs the
  sweep skipped 5–6 in-flight sessions per cycle and still swept all true
  orphans (including the deliberate leak) — so the skip did not starve the sweep
  at this load.
- **Drain timeout (added by the correction).** The pre-snapshot drain is bounded
  by `max(waveMs, 2 min)`; if a straggler outlives it, the run finalises anyway
  and records the still-live children (`liveChildrenAtEndSnapshot` + ids) rather
  than blocking. In that case the end snapshot legitimately contains live
  children, and the report says so (`live children at the snapshot: N`) instead
  of implying retention. Both live runs drained cleanly (`drained=true`,
  `live=0`), so the bound has not yet been exercised in practice.
- **`--hours` window vs a long wave.** The wave loop is now bounded by the
  window, but in-flight stragglers still settle in the background after the
  window (by design — they are real sessions); for very short windows the end
  snapshot may therefore include recently-completed children.
- **`git log -1 -- server/src shared/src` uses the committer date.** A rebase or
  a commit with a rewritten/backdated committer timestamp could make a fresh
  build look stale (refusal is the safe direction) or, in principle, a stale
  build look fresh (a backdated commit); the guard's normal case — build after
  commit — is unaffected.
- The stale-build guard is mtime-based, not content-based: a `dist` rebuilt from
  the same source but then left while a *newer* commit with the same second
  lands is accepted at equal second granularity (test covers the equality case
  deliberately).
- **Micro-run observation, not a B0.1 finding.** The end-snapshot retainer
  summary names `AgentSession` (5 instances via
  `object:global / --property:__PIWEBUI_LOGGER__-->`). At the end of a micro run
  stragglers are still in flight, so a handful of live sessions is expected; it
  is an A1/B1 question whether any of those are disposed-and-retained, not a
  B0.1 one. Flagged here so it is not later mistaken for new evidence.
- **Untracked orphans (correction 04) are reconciled, not retained.** A session
  whose `createSession` is in flight across a supervisor kill has no
  `child_created` event; the server-side reconciliation now sweeps it as
  `orphan_swept` (`untracked`) and the report counts it as live-on-server, never
  as retained. If a `Retained deleted child` still appears after correction 04,
  it is a real B1-class finding and must name its retainer.
- **Micro-run sample coverage 113/121 (93.4%)**, below A1's 95% target, with a
  largest gap of 1.6 intervals. A Gate 1 micro run deliberately `SIGKILL`s the
  supervisor mid-run (the reattach control) and takes start/end heap snapshots,
  both of which cost samples; this is not a B0.1 criterion and not a regression
  from these changes.
